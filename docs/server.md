# Server notes (M2c)

Design record for the `mtg-server` game actor. Rules of the house are in `CLAUDE.md`; the wire contract is in `protocol.md`.

## Shape
- `spawn_game(id, setup, store)` starts a game in its lobby; `resume_game(store, id, setup)` rebuilds one from its log. Both return a cheap-clone `GameHandle` (`join(seat) -> Receiver<ServerMessage>`, `send(seat, ClientMessage)`, `leave(seat)`, `status()`) and must run inside a tokio runtime.
- One task per game owns the `Engine`, the `EventStore` and a bounded queue per seat. A full or abandoned queue drops that client, which reconnects and receives a snapshot; the actor never waits for a client.
- Lobby: only joins and `Ready`. The last `Ready` creates the engine and broadcasts the opening events from seq 0. A resumed game goes straight to running; one with an empty log returns to the lobby.
- One step: check seat, `DecisionId` and engine legality, run `apply` or `concede`, project for the connected seats, append to the store, then send the events, the next `Decision` (only to the seat it names) and `GameOver`. A store or projection failure restores the engine from its `Checkpoint` and answers `Error{Internal}` without details.
- Join and `Resync` send `Welcome`, a `Snapshot` and the seat's pending decision. The game waits for disconnected seats; there is no auto-pass.

## Contract for the transport
- The actor trusts the seat it is given. The transport must map a credential to exactly one seat and never let a client name its own.
- A replaced socket drops its receiver instead of calling `leave`, which closes whatever connection the seat has at that moment.
- `status()` exposes the state hash and is for tests and admin views, never for clients.
- `GameId::random()` (uuid v4) names every new game.
- A `GameSetup` holds an `Arc<dyn FormatRules>`, so what is stored is a serializable `GameRecipe` (format, seed, decks); see Persistence.

## Persistence
- `PgEventStore::new(pool)` implements `EventStore` over table `game_events (game_id uuid, seq bigint, event jsonb, created_at)`, primary key `(game_id, seq)`: one row per engine event, serialised with serde (`Event` as externally tagged JSON). `read_from(game, seq)` returns the tail; `load` is `read_from(game, 0)`.
- An append is one transaction holding a per-game advisory lock (`pg_advisory_xact_lock(class, hashtext(game))`): it checks that the log ends at `from_seq`, then inserts the whole batch with one `unnest(...) WITH ORDINALITY` statement, so a gap, a repeat or a lost race returns `OutOfOrder` with the stored count and a failure midway leaves no rows. The primary key backs the lock up. The actor's rollback needs nothing from the store, because it restores its `Engine` from a `Checkpoint` and only appends after the step succeeded.
- Reads check that sequence numbers run without a gap and that every event decodes, else `StoreError::Corrupt`; connection and SQL failures are `Unavailable`.
- Migrations live in `crates/mtg-server/migrations` and are tracked in `_mtg_server_migrations`, not `_sqlx_migrations` (which `mtg-db` owns), so the two crates migrate one database in any order, repeatedly and concurrently. `mtg_server::migrate(&pool)` runs them; the table name is part of the on-disk contract and must never change. `sqlx::test` suites must use `migrations = false` and call `migrate`, since the default would use `_sqlx_migrations`.
- Refresh `.sqlx/` after changing a query: create a scratch database, apply `crates/mtg-server/migrations/*.sql` to it, then run `SQLX_OFFLINE=false DATABASE_URL=<scratch db> SQLX_OFFLINE_DIR=<repo>/.sqlx cargo check -p mtg-server`.
- Game records: `games (id, status, recipe jsonb, result jsonb, failure, created_at, started_at, finished_at)` and `seats (game_id, seat, name, token_digest bytea, joined)`, written by `GameRecords`. `status` is `lobby`, `running`, `finished`, `expired` (the janitor dropped it) or `failed` (it could not be loaded on boot). Only the SHA-256 of a seat token is stored; tokens exist in clear once, in the create response. `game_events` has no foreign key to `games`.
- `GameRecipe {format, seed, decks}` (`DeckRef::Demo{id}` today, room for card lists) is the only way the server builds a `GameSetup`, for a new game and a resumed one alike; its JSON (`{"format":"normal","seed":..,"decks":[{"kind":"demo","id":..}]}`) is an on-disk contract, unknown fields and variants are refused. A game made with `Registry::register(setup, ..)` has no recipe, so it is never recorded.
- `Registry::create` (now async) writes game and seats in one transaction before the actor exists, so a failed write creates nothing (REST answers 503). The actor carries a `Recorder` and notes the first join of each seat, the start (`running`) and the end (`finished`, with the result, before `GameOver` is sent). A failed write is logged and never stops a game, because the log is the truth: boot repairs a status that lags behind it.
- Resume: `Server::open(config, pool)` (or `Registry::with_database` plus `resume()`) loads every `lobby` and `running` game oldest first, rebuilds the setup from its recipe, checks the seat rows against it, calls `resume_game` and keeps the stored digests, so old tokens still open the same seats. A game whose log shows it ended is only corrected to `finished`. A recipe, seat rows or log that do not load (including a panic while replaying) mark the game `failed` with the reason, log it and move on; only an unreachable database stops the boot. A `failed` game is not retried; fix the row and set it back to `running` by hand.
- Lobbies survive a restart as records with an empty log: they come back as lobbies, everyone must send `Ready` again (readiness is not stored), and they keep their age, so one older than `Retention::lobby_after` (1 h, by the database clock) is `expired` instead. Resumed running games get a fresh 24 h without a connection. The cap `MTG_MAX_GAMES` limits creation only; every stored game resumes. When the janitor drops a game it marks the record `expired` (or `finished`), so a dropped game stays dropped.
- The binary reads `DATABASE_URL`: set, it connects (10 connections), runs `migrate`, then `Server::open`; unset or empty, it logs a warning and keeps every game in memory. `.cargo/config.toml` sets a default URL for `cargo run` (local Postgres: `docker compose up -d db`); `DATABASE_URL= cargo run -p mtg-server` runs without a database. The URL is never logged.
- Not detected: `Engine::resume` applies stored events as facts, so a log replayed under a recipe with other decks or another seed does not fail. Recipes are only written at creation, so this matters when demo deck contents change.

## Accounts
- Tables (migration `20261018000003_users.sql`, same `_mtg_server_migrations` table): `users (id, username, username_key, password_hash, created_at)` and `sessions (token_digest, user_id, created_at, expires_at)`. `username` is kept as typed and shown as typed; `username_key` is its lower case and unique, which makes names unique ignoring case. `CHECK`s repeat the server's rules (`[A-Za-z0-9_-]{3,32}`, key = `lower(username)`), so the database refuses what the server would. A session is the SHA-256 of its cookie token (primary key, like the seat tokens), deleted with its user. Accounts need Postgres: a server without `DATABASE_URL` answers every account endpoint 503 `accounts_unavailable` and its games are guest-only.
- Rules: a username is 3 to 32 ASCII letters, digits, `_` or `-` (no trimming, no Unicode, so no look-alikes); a password is 10 to 128 characters (Unicode scalar values), compared byte for byte, never trimmed or normalised. The limits are constants in `mtg_protocol::rest`. Passwords are hashed with Argon2id (`argon2` 0.6.0, pinned exactly) and stored as the PHC string, so the cost travels with the hash and a later change of `HashCost` leaves old hashes valid. The default is the OWASP minimum (19 MiB, 2 passes, 1 lane, about 30 ms); `HashCost::cheapest()` (8 KiB, 1 pass) is for tests. Hashing runs on `spawn_blocking` behind a semaphore (`AuthConfig::hash_jobs`, 4), so a burst of requests cannot exhaust memory.
- Endpoints (bodies `Credentials` and `UserView` from `mtg_protocol::rest`, errors `{error, message}` with the codes of `AuthErrorCode`):
  - `POST /api/auth/register` {username, password} gives 201 {id, username} and signs the new account in (Set-Cookie). 400 `invalid_username` / `invalid_password` (the message states the rule, never the input), 409 `username_taken`, 403 `registration_closed` (`MTG_REGISTRATION=closed`, decided before the body is read), 429.
  - `POST /api/auth/login` gives 200 {id, username} and a fresh session. Any failure on the merits is 401 `invalid_credentials` with one fixed body: unknown username, wrong password, and a username or password that breaks the rules (which cannot belong to an account and so costs no hashing) are byte-identical. 429 `too_many_attempts` with `Retry-After`.
  - `POST /api/auth/logout` deletes the session and clears the cookie; 204 whether or not there was one.
  - `GET /api/auth/me` gives 200 {id, username} or 401 `unauthenticated`; a request that presented a cookie the server does not honour (expired, deleted) gets it cleared in the answer.
  - Signing in or registering while the browser presents a session ends that session first, so one browser holds one. Other browsers' sessions are left alone.
- The cookie `mtg_session` holds 256 random bits as hex (from the operating system's CSPRNG through `getrandom`, like seat tokens) and nothing else: `HttpOnly; SameSite=Lax; Path=/; Max-Age=2592000` (30 days, `AuthConfig::session_lifetime`), no `Domain`, plus `Secure` when `MTG_COOKIE_SECURE=1` (set it behind TLS). The expiry is absolute, not sliding, and is judged by the database's clock (`expires_at > now()`). An upkeep task deletes expired rows every hour (`purge_every`) and makes the stand-in hash at start.
- Login does not reveal whether a username exists: the same 401 body, and one Argon2 check either way (an unknown name is checked against a stand-in hash made at start with the same cost from a random password nobody knows, and the result is discarded). Registration does say "taken"; that cannot be avoided.
- Guessing is throttled in memory per process (`throttle.rs`): fixed windows (`AttemptLimits`, default 15 minutes) count failed logins per client address (30) and per username (10, whether or not the account exists) and registrations per address (10). A login is counted when it starts, so parallel guesses cannot slip under the limit, and handed back when it succeeds (the username starts afresh) or when the server could not check it (database down). Over the limit the answer is 429 with `Retry-After` even for the right password, and a blocked try is not counted. IPv6 addresses are grouped by /64, IPv4-in-IPv6 as IPv4. A hostile client can lock a username out for one window; the lock expires by itself. The table is capped at 50 000 counters; past that, keys not yet tracked go unlimited until a sweep frees room.
- The client address is the socket's peer. Behind a reverse proxy set `MTG_TRUSTED_PROXIES=n` (0 to 16, default 0): the address is then the `n`-th entry from the right of `X-Forwarded-For`, which the nearest trusted proxy wrote, so entries a client forged to the left are ignored; a short or malformed header falls back to the peer. With 0 the header is ignored, because anybody can send it. The server must be served with connect info (`Server::serve` does).
- Passwords, tokens, digests and hashes never reach logs or `Debug` output: `Credentials`, `SessionToken`, `SeatToken`, `TokenDigest` and the stored hash print `<redacted>` or nothing, failed attempts are logged without the name tried, and a test captures every log line at TRACE during a whole sign-up and sign-in and searches it.
- `AuthConfig` (in `ServerConfig::auth`): `registration`, `cookie_secure`, `session_lifetime`, `hash_cost`, `hash_jobs`, `limits`, `trusted_proxies`, `purge_every`; only the first, second and seventh come from the environment. A database failure is 503 `unavailable` without details (logged) and costs no throttle budget.

## Tests
- `tests/pg_accounts.rs` (Postgres, real HTTP): the whole sign-up, sign-in, who-am-I and sign-out cycle and the cookie's exact attributes with and without `Secure`; username and password limits as a table; case-insensitive uniqueness (also enforced by the database); malformed bodies; digests and hashes only in the tables; byte-identical failed logins; throttling per username, per address behind a trusted proxy, with a forged `X-Forwarded-For`, and registrations; closed registration; expiry, purge and replacement of sessions; foreign origins on every POST; CORS credentials; the server without a database; a failing database; racing registrations; the logs searched for secrets. Unit tests cover the rules (`credentials.rs`), hashing (`passwords.rs`), the cookie (`cookie.rs`), the counters with an injected clock (`throttle.rs`), the forwarded-address rule (`auth.rs`) and the environment (`config.rs`).
- `tests/store_contract.rs` runs one contract (round trip, empty appends, gaps and repeats, game isolation, racing appends with exactly one winner, whole-batch races) against `MemoryStore` and `PgEventStore`; `pg_store.rs` covers real game logs, `read_from`, a failing batch, damaged rows and an unreachable database; `pg_migrations.rs` runs both migrators in each order, repeatedly and concurrently; `pg_game.rs` plays and resumes whole bot games on Postgres; `pg_records.rs` checks what creating, joining, starting and finishing write (digests only, atomic creation, 503 when the database is down); `pg_resume.rs` restarts the server on the same pool (handle bots and real sockets with the old tokens, finished, lobby, expired, janitor-dropped and damaged games, token isolation).
- Bot clients play through the handle only; the actor's log equals the same game run on a bare engine (2 to 4 seats), 30 concurrent games finish, a reconnect continues to the uninterrupted result, and a failing store leaves the game unchanged.

## Transport
- `Server::new(config).serve(listener, shutdown)` runs axum; the `mtg-server` binary reads `MTG_BIND` (127.0.0.1:8080), `MTG_ALLOWED_ORIGINS` (comma list), `MTG_MAX_GAMES` (100) and, for accounts, `MTG_REGISTRATION`, `MTG_COOKIE_SECURE` and `MTG_TRUSTED_PROXIES` (see Accounts). `ServerConfig::fixed_seed` is for tests only and is never read from the environment.
- REST: `POST /api/games` {format:"normal", seats:[{name, deck}]} gives 201 {game, seats:[{seat, token}]} (2 to 12 seats, 16 KiB `application/json` body, unknown fields refused, the seed is always server-random); `GET /api/games/{id}` gives {started, seats, connected, result}; `GET /api/decks`; `GET /healthz`; the account endpoints below. Errors are `{error, message}`.
- Every request that changes something (any method but GET, HEAD and OPTIONS) goes through `api::same_site_only`: an `Origin` that is neither in `MTG_ALLOWED_ORIGINS` nor the request's own `Host` is 403 `forbidden_origin`, no `Origin` (a bot) passes. It is the socket's rule (`origin.rs`), applied to POSTs too. CORS answers listed origins only and now sends `Access-Control-Allow-Credentials: true` to them, so a front end on a listed origin may send the session cookie.
- `Registry` holds the games: tokens are 256 random bits from the OS and only their SHA-256 is kept (never logged); a cap on games; a janitor drops finished games after 10 min, lobbies that never started after 1 h and started games nobody has been connected to for 24 h.
- `GET /ws/{game}/{token}`: the token picks the seat before the upgrade (unknown game, malformed id and wrong token share one 404); `Origin` must be listed or match `Host` (no `Origin` is a bot and passes). Then `Join` within 10 s (wrong version gets `Error{UnsupportedVersion}`, a mismatching game `Error{UnknownGame}`), `handle.join(seat)`, and one text frame per `ClientMessage`/`ServerMessage`.
- Limits per socket: frames at most 64 KiB, a burst of 40 messages then 20 per second, five malformed messages in a row, ping every 20 s and a close after 60 s without a pong. A second socket for a seat replaces the first.
- Close codes: 1001 server stopping or game removed, 1002 bad handshake, 1007 not UTF-8, 1008 policy (rate, malformed run, no join, no pong), 1009 frame too big, 1013 dropped as too slow (reconnect), 4000 replaced by a newer socket of the same seat (do not reconnect on your own). A closed socket drops the seat's queue and never calls `leave`.
- Shutdown (SIGTERM or ctrl-c): stop accepting, send every socket 1001, wait up to 5 s for all of it; a stalled request cannot hold the process.
- Tests (`tests/{ws_games,ws_refusals,ws_limits,rest,registry,shutdown}.rs`, helpers in `tests/net/`) use a real listener on port 0, raw TCP for hostile HTTP and tokio-tungstenite for sockets.
