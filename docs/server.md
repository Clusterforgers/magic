# Server notes (M2c)

Design record for the `mtg-server` game actor. Rules of the house are in `CLAUDE.md`; the wire contract is in `protocol.md`.

## Shape
- `spawn_game(id, setup, store)` starts a game in its lobby; `resume_game(store, id, setup)` rebuilds one from its log. Both return a cheap-clone `GameHandle` (`join(seat) -> Receiver<ServerMessage>`, `send(seat, ClientMessage)`, `leave(seat)`, `status()`) and must run inside a tokio runtime.
- One task per game owns the `Engine`, the `EventStore` and a bounded queue per seat. A full or abandoned queue drops that client, which reconnects and receives a snapshot; the actor never waits for a client.
- Lobby: joins, `Ready`, `NotReady` and chat. Readiness is one flag per seat in `Phase::Lobby { ready, names }`, never stored: it outlives a connection (a seat that is ready and away stays ready), `NotReady` takes it back, and a `Ready` or `NotReady` after the start is ignored. The last `Ready` creates the engine and broadcasts the opening events from seq 0. A resumed game goes straight to running; one with an empty log returns to the lobby with nobody ready.
- Lobby roster (`lobby.rs`): `ServerMessage::Lobby { seats: [{seat, name, connected, ready}], needed }` goes to every connected seat after its `Welcome` and again whenever the table changes: a seat joins, a client goes away, `Ready` or `NotReady` flips a flag. `needed` is the seats not ready. A repeat that changes nothing says nothing, a connection that takes a seat over from another is the only one sent the roster, and the `Ready` that starts the game sends none (the opening events are the news; a start that fails does send one, with everybody ready). A hang-up sends nothing to the actor, so queues that closed are looked for after every command (`announce_departures`; `Seats::take_gone` remembers a queue dropped by a sweep, a send to a closed queue or a full one, so a lookup or chat line that meets it first cannot hide it) and, while the lobby is idle, waited for (`Seats::client_gone` in the actor loop). A client dropped for being too slow is told to the others in a second roster. Names are what the game was made with (`Registry` passes them to `spawn_named`; a game spawned directly calls its seats "Seat N"). `GameStatus.ready` and the REST `ready` list the flags (every seat once the game runs).
- One step: check seat, `DecisionId` and engine legality, run `apply` or `concede`, project for the connected seats, append to the store, then send the events, the next `Decision` (only to the seat it names) and `GameOver`. A store or projection failure restores the engine from its `Checkpoint` and answers `Error{Internal}` without details.
- Join and `Resync` send `Welcome`, a `Snapshot` and the seat's pending decision. The game waits for disconnected seats; what it does for a seat by itself is the auto-pass for a seat with nothing to do, the passes for a seat that yields and the answer at the deadline of a response clock (Pace of play).

## Pace of play (`pace.rs`, `yields.rs`)
- **Auto-pass.** `ClientMessage::AutoPass { enabled }` sets one flag per seat, kept in the actor (not stored): it starts at `GameConfig::pace.auto_pass` (`MTG_AUTO_PASS`, default on), a flag set in the lobby holds for the game, and a resumed game starts every seat at the server default again. `Welcome` carries the seat's flag (`auto_pass`), so a client that reconnects, or whose server restarted, shows what the server holds. There is no other reply; the effect is the next messages.
- When a step leaves a pending `Priority` decision whose `can_act` is false for a seat with the flag on, the actor answers `Pass` for it and never sends the decision (`Running::skip_idle`). The passes are the engine's own `apply`, repeated, and their events are appended to the step that caused them, so the answer and the passes after it are one projection, one `append` and one batch, and if the save fails the whole stretch is rolled back from the first checkpoint (the sender gets the usual `Error{Internal}`). The run stops at any other decision (a land to play, a spell, an attack, blocks, a discard, a payment...), at a seat with the flag off, and at the end of the game; at most `MAX_IDLE_PASSES` (500) passes go in one step, after which the decision is sent as it is, so one batch stays small and a table with nothing to do for dozens of turns cannot stall the actor.
- Turning the flag on while the seat faces an idle window passes at once. A game resumed from its log, and a scenario that starts on an idle decision, get the same treatment before any client connects (`start_up`).
- Reference: `PlayOptions::auto_pass` in `mtg-testkit` plays bot games under the same rule; `tests/auto_pass.rs` checks the actor's log, hash and result against it for 2 to 4 seats and that no bot is ever sent an idle decision.
- **Yields.** `ClientMessage::Yield { until }` (`Resolve`, `EndOfTurn`, `MyTurn`) and `CancelYield` set and end a per-seat yield kept in the actor (`yields: Yields`, not stored: a resumed game starts with none; `Welcome.yielding` and `ServerMessage::Yielding` tell the seat, see `protocol.md`). The rules that decide when a yield stops are all in one function, `Active::ends_at` in `yields.rs` (the module doc lists them), judged at each priority decision of the seat from the table alone: `Resolve` when the stack is empty, `EndOfTurn` when a turn other than the one it was asked in has begun, `MyTurn` when such a turn is the seat's own, and any yield when another seat has put an object on the stack that the seat has not passed on. They never look at what the seat could do (`can_act`), so a seat that can respond and one that cannot are passed for, stopped and hurried at the same moments and the pace tells nothing about a hand. Stops per step and holding priority wait for instants and activated abilities (M3). `pace::passes_for` is the one test the run of passes asks of each decision: the decision is a priority decision and (the seat yields, or it is idle with auto-pass on); a yield the decision ends is dropped and auto-pass then decides.
- The passes are `Running::skip_idle` (the run that serves auto-pass): the answer, the passes that follow it and the save are one unit, so a failed save restores the engine and also keeps the yields as they were (`publish` starts from a copy of them and keeps it only once saved). `set_yield` starts the copy and, if the seat faces a priority decision, runs an empty step through the same path, so the decision is passed at once; if the yield ends there (`Resolve` over an empty stack) the decision is issued again with a new id and nothing is passed, so a client that dropped its prompt is never left without one. A yield set while the seat has no priority decision pending is just stored and told. After a successful step the yields of seats that left the game (and all of them once it is over) are dropped, and every seat whose yield changed is sent `Yielding` after the batches and before the decision (`announce`). The 500-pass cap of one step applies to all passes together; when it cuts a run at a priority decision of a yielding seat that seat's yield ends (with a notice) and the decision is sent, so a yielding seat is never sent a prompt that the server still "passes for". A `Yield` before the game starts, after it ended or from a seat that is out is `Error{BadMessage}`; `CancelYield` with nothing to cancel says nothing.
- **Stops and Full Control** (`stops.rs`, Game flow (d1)). `ClientMessage::SetStop` and `ClientMessage::FullControl` fill a per-seat set of stops and a per-seat Full Control mode kept in the actor (`stops: Stops`, not stored: a resumed game starts with none, kept across reconnects; `Welcome.stops`, `Welcome.full_control`, `ServerMessage::Stops` and `ServerMessage::FullControl` tell the seat, see `protocol.md`). **They are stored and reported only**: nothing that decides when a seat is asked (`pace::passes_for`, the clocks, the yields) reads them until Game flow (d2) (stops) and (d4) (Full Control). The rules are in `stops.rs`: a stop must be in a step where a player gets priority (`Step::grants_priority`, so untap and cleanup are refused, set or cleared, with `Error{BadMessage}` and no resync), a seat holds each side and step once, setting a held stop again replaces its `keep` (kept per stop for d2: false until its step has passed once), and a request that changes nothing the seat can see says nothing. Setting takes no engine step: nothing is saved, no decision is issued again and the pending id stays valid. The lobby accepts them (they hold for the game); a seat that is out of the game, or a game that is over, gets `Error{BadMessage}`. A change goes through `commit_stops`, which compares the old and the new `Stops` (`Stops::replace`) and tells each seat whose list or mode changed.
- A step starts from a copy of the stops as it does from one of the yields (`publish_with`) and keeps it only once the step is saved. Today the only change a step makes is `Stops::drop_finished`: a seat that left the game, and every seat once it is over, holds nothing and is told after the events and the yield notices and before the next decision or `GameOver`; a failed save leaves them as they were. Game flow (d2) clears one-turn stops in the same place.
- **Response clocks.** A decision gets its clock when it is issued (`Running::settle`, `Pace::clock_for`): a `Priority` decision while the seat is not the active player, `MTG_RESPONSE_SECS` (default 10 s), whether the seat can act or not (an idle window, delivered when its auto-pass is off, would hold the table for nothing; and the same clock for both means the table cannot tell a hand from its pace), and `DeclareBlockers` of a defending seat, `MTG_BLOCK_SECS` (45 s); `0` switches a clock off and nothing above a day is accepted. Every other decision (mulligan, bottom, discard, payment, attackers, damage division, whatever the active player is asked) has none and waits as long as it takes. The clock does not depend on the auto-pass setting, runs whether the seat is connected or not, is stopped by any answer, and starts afresh when a game is resumed from its log.
- The decision message carries the time left in `deadline_ms` (absent without a clock): the whole clock when it is issued, and what is left when the decision is sent again after a join or `Resync`, so a client's own clock never matters.
- At the deadline the actor answers for the seat with the safe default, `Running::fall_back`: a pass, or no blocks. That is `Running::answer` for the seat, so the move is checked, saved, projected and followed by the auto-passes like the seat's own; the decision's id is gone afterwards, so a late answer from the client is the ordinary `StaleDecision`. The actor's loop is a `select!` between its next command and the `due` time of the pending decision, commands first: a command already waiting was sent before the clock ran out. When the move cannot be saved the engine is restored, the seat is told `Error{Internal}` like for any failed save, the decision stays and its clock moves one second ahead, so a failing store is retried at a pace and never spun on.
- Tests use tokio's paused time (`start_paused`, `time::advance`, the `test-util` feature in the dev-dependencies): `tests/response_clock.rs`.

## Previews
- `ClientMessage::Preview` is answered by the actor itself (`preview.rs`, `Running::preview`) with one `Forecast` to the sender. The decision id must be the pending one for that seat; then `Engine::preview_forecast` judges the answer. Everything else gives `forecast: null` and never an `Error` (a stale id, a foreign one, an answered decision, a non-combat decision, an answer the engine refuses, no game yet), because the stale-decision treatment of `Answer` would raise a notice and a resync in a client whose preview raced with its real answer. Nothing is applied, projected, stored, logged or sent to another seat, so the event log, the store and the state hash stay as they were (tests compare all three).
- Rate limit: a token bucket per seat inside the actor (`PreviewLimits`; `PREVIEW_BURST` 20, then `PREVIEWS_PER_SECOND` 10), kept for the life of the game so a reconnect does not refill it. A preview over the limit is answered with a null forecast without touching the engine, so the client is never left waiting. Real answers have no bucket and queue behind previews like any message; the previews the bucket lets through cost one clone of the state each (5 to 8 µs), at most 20 in a burst, so a flood cannot starve an answer (a test sends 150 previews and an answer straight after). The socket limit (40 messages, then 20 a second) applies to every frame, previews included.
- Who may preview: every socket is bound to one seat by its credential before the upgrade and must open with `Join`, so there are no unseated or spectator sockets to refuse; a `Preview` as the first frame is refused like any other message (`Error{BadMessage}`, close 1002), and a message for a seat the game does not have is ignored.

## Contract for the transport
- The actor trusts the seat it is given. The transport must map a credential to exactly one seat and never let a client name its own.
- A replaced socket drops its receiver instead of calling `leave`, which closes whatever connection the seat has at that moment.
- `status()` exposes the state hash and is for tests and admin views, never for clients.
- `GameId::random()` (uuid v4) names every new game.
- A `GameSetup` holds an `Arc<dyn FormatRules>`, so what is stored is a serializable `GameRecipe` (format, seed, decks); see Persistence.

## Persistence
- `PgEventStore::new(pool)` implements `EventStore` over table `game_events (game_id uuid, seq bigint, event jsonb, created_at)`, primary key `(game_id, seq)`: one row per engine event, serialised with serde (`Event` as externally tagged JSON). `read_from(game, seq)` returns the tail; `load` is `read_from(game, 0)`.
- An append is one transaction holding a per-game advisory lock (`pg_advisory_xact_lock(class, hashtext(game))`): it checks that the log ends at `from_seq`, then inserts the whole batch with one `unnest(...) WITH ORDINALITY` statement, so a gap, a repeat or a lost race returns `OutOfOrder` with the stored count and a failure midway leaves no rows. The primary key backs the lock up. The actor's rollback needs nothing from the store, because it restores its `Engine` from a `Checkpoint` and only appends after the step succeeded.
- Reads check that sequence numbers run without a gap and that every event decodes, else `StoreError::Corrupt`; connection and SQL failures are `Unavailable`.
- Migrations live in `crates/mtg-server/migrations` and are tracked in `_mtg_server_migrations`, not `_sqlx_migrations` (which `mtg-db` owns), so the two crates migrate one database in any order, repeatedly and concurrently. `mtg_server::migrate(&pool)` runs them; the table name is part of the on-disk contract and must never change. `sqlx::test` suites must use `migrations = false` and call `migrate`, since the default would use `_sqlx_migrations`.
- Refresh `.sqlx/` after changing a query: create a scratch database, apply `crates/mtg-server/migrations/*.sql` to it, then run `SQLX_OFFLINE=false DATABASE_URL=<scratch db> SQLX_OFFLINE_DIR=<repo>/.sqlx cargo check -p mtg-server`.
- Game records: `games (id, status, recipe jsonb, result jsonb, failure, created_at, started_at, finished_at)` and `seats (game_id, seat, name, token_digest bytea, joined, user_id)`, written by `GameRecords` (`user_id` is the account the seat is bound to, see Accounts). `status` is `lobby`, `running`, `finished`, `expired` (the janitor dropped it) or `failed` (it could not be loaded on boot). Only the SHA-256 of a seat token is stored; tokens exist in clear once, in the create response. `game_events` has no foreign key to `games`.
- `GameRecipe {format, seed, decks, fingerprints}` (`DeckRef::Demo{id}` today, room for card lists) is the only way the server builds a `GameSetup`, for a new game and a resumed one alike; its JSON (`{"format":"normal","seed":..,"decks":[{"kind":"demo","id":..}],"fingerprints":["v1:<64 hex digits>",..]}`) is an on-disk contract, unknown fields and variants are refused, and `fingerprints` is absent in a recipe stored before it existed (serde default, and not written while empty); a server older than the field refuses a recipe that has it, like any unknown field, so a rollback past this change fails the games created since. A game made with `Registry::register(setup, ..)` has no recipe, so it is never recorded.
- `Registry::create` (now async) writes game and seats in one transaction before the actor exists, so a failed write creates nothing (REST answers 503). The actor carries a `Recorder` and notes the first join of each seat, the start (`running`) and the end (`finished`, with the result, before `GameOver` is sent). A failed write is logged and never stops a game, because the log is the truth: boot repairs a status that lags behind it.
- Resume: `Server::open(config, pool)` (or `Registry::with_database` plus `resume()`) loads every `lobby` and `running` game oldest first, rebuilds the setup from its recipe, checks the seat rows against it, calls `resume_game` and keeps the stored digests, so old tokens still open the same seats. A game whose log shows it ended is only corrected to `finished`. A recipe, seat rows or log that do not load (including a panic while replaying) and a deck that changed since the game was created (next bullet) mark the game `failed` with the reason, log it and move on; only an unreachable database stops the boot. A `failed` game is not retried; fix the row and set it back to `running` by hand. A failed game is not loaded, so tokens, `GET /api/games/{id}` and both socket routes answer as for a game that never existed (404), and `/api/me/games` never lists it.
- Lobbies survive a restart as records with an empty log: they come back as lobbies, everyone must send `Ready` again (readiness is not stored), and they keep their age, so one older than `Retention::lobby_after` (1 h, by the database clock) is `expired` instead. Resumed running games get a fresh 24 h without a connection. The cap `MTG_MAX_GAMES` limits creation only; every stored game resumes. When the janitor drops a game it marks the record `expired` (or `finished`), so a dropped game stays dropped.
- The binary reads `DATABASE_URL`: set, it connects (10 connections), runs `migrate`, then `Server::open`; unset or empty, it logs a warning and keeps every game in memory. `.cargo/config.toml` sets a default URL for `cargo run` (local Postgres: `docker compose up -d db`); `DATABASE_URL= cargo run -p mtg-server` runs without a database. The URL is never logged.
- Deck check (`recipe/fingerprint.rs`): `Engine::resume` applies stored events as facts, so a log would replay under other cards without failing, and a recipe names a demo deck only by id. A new game's recipe therefore also stores one `DeckFingerprint` per seat (`GameRecipe::with_fingerprints`, called by `Registry::create`): the SHA-256 of a canonical, versioned text of the ordered cards the engine is given (`mtg-deck/v1`, the count, then each card's serde JSON with sorted keys), written `v1:<hex>`. `GameRecipe::build` recomputes it and fails with `RecipeError::DeckChanged { seat, .. }` for the first seat whose cards differ in any field, in order or in size; resume then marks the game `failed` with "the deck changed: seat N (..)" before replaying anything and logs it at error level (`game`, `seat`, `reason`). A recipe stored before fingerprints existed resumes unchecked, with a warning at every boot. A new field on `CardDefinition` changes every fingerprint unless it is skipped in the JSON while it holds its default (the pinned values in the tests fail), and a new encoding needs a new version (a version this server does not read fails the recipe's decoding, never the check). A changed seed, format rule or engine is still not detected.

## Accounts
- Tables (migration `20261018000003_users.sql`, same `_mtg_server_migrations` table): `users (id, username, username_key, password_hash, created_at)` and `sessions (token_digest, user_id, created_at, expires_at)`. `username` is kept as typed and shown as typed; `username_key` is its lower case and unique, which makes names unique ignoring case. `CHECK`s repeat the server's rules (`[A-Za-z0-9_-]{3,32}`, key = `lower(username)`), so the database refuses what the server would. A session is the SHA-256 of its cookie token (primary key, like the seat tokens), deleted with its user. Accounts need Postgres: a server without `DATABASE_URL` answers every account endpoint 503 `accounts_unavailable` and its games are guest-only.
- Rules: a username is 3 to 32 ASCII letters, digits, `_` or `-` (no trimming, no Unicode, so no look-alikes); a password is 10 to 128 characters (Unicode scalar values), compared byte for byte, never trimmed or normalised. The limits are constants in `mtg_protocol::rest`. Passwords are hashed with Argon2id (`argon2` 0.6.0, pinned exactly) and stored as the PHC string, so the cost travels with the hash and a later change of `HashCost` leaves old hashes valid. The default is the OWASP minimum (19 MiB, 2 passes, 1 lane, about 30 ms); `HashCost::cheapest()` (8 KiB, 1 pass) is for tests. Hashing runs on `spawn_blocking` behind a semaphore (`AuthConfig::hash_jobs`, 4), so a burst of requests cannot exhaust memory.
- Endpoints (bodies `Credentials` and `UserView` from `mtg_protocol::rest`, errors `{error, message}` with the codes of `AuthErrorCode`):
  - `POST /api/auth/register` {username, password} gives 201 {id, username} and signs the new account in (Set-Cookie). 400 `invalid_username` / `invalid_password` (the message states the rule, never the input), 409 `username_taken`, 403 `registration_closed` (`MTG_REGISTRATION=closed`, decided before the body is read), 429.
  - `POST /api/auth/login` gives 200 {id, username} and a fresh session. Any failure on the merits is 401 `invalid_credentials` with one fixed body: unknown username, wrong password, and a username or password that breaks the rules (which cannot belong to an account and so costs no hashing) are byte-identical. 429 `too_many_attempts` with `Retry-After`.
  - `POST /api/auth/logout` deletes the session and clears the cookie; 204 whether or not there was one.
  - `GET /api/auth/me` gives 200 {id, username} or 401 `unauthenticated`; a request that presented a cookie the server does not honour (expired, deleted) gets it cleared in the answer.
  - Signing in or registering while the browser presents a session ends that session first, so one browser holds one. Other browsers' sessions are left alone.
- The cookie `mtg_session` holds 256 random bits as hex (from the operating system's CSPRNG through `getrandom`, like seat tokens) and nothing else: `HttpOnly; SameSite=Lax; Path=/; Max-Age=2592000` (30 days, `AuthConfig::session_lifetime`), no `Domain`, plus `Secure` when `MTG_COOKIE_SECURE=1` (set it behind TLS). The expiry is absolute, not sliding, and is judged by the database's clock (`expires_at > now()`). An upkeep task deletes expired rows every hour (`purge_every`) and makes the stand-in hash at start.
- Login does not reveal whether a username exists: the same 401 body, and one Argon2 check either way (an unknown name is checked against a stand-in hash made at start with the same cost from a random password nobody knows, and the result is discarded). Registration does say "taken"; that cannot be avoided.
- Guessing is throttled in memory per process (`throttle.rs`): fixed windows (`AttemptLimits`, default 15 minutes) count failed logins per client address (30) and per username (10, whether or not the account exists) and registrations per address (10). A login is counted when it starts, so parallel guesses cannot slip under the limit, and handed back when it succeeds (the username starts afresh) or when the server could not check it (database down). Over the limit the answer is 429 with `Retry-After` even for the right password, and a blocked try is not counted. The try that uses a limit up is logged once at warn (without the name tried) and the tries turned away after it at debug, so a client that keeps knocking cannot fill the log. IPv6 addresses are grouped by /64, IPv4-in-IPv6 as IPv4. A hostile client can lock a username out for one window; the lock expires by itself. The table is capped at 50 000 counters; past that, keys not yet tracked go unlimited until a sweep frees room.
- The client address is the socket's peer. Behind a reverse proxy set `MTG_TRUSTED_PROXIES=n` (0 to 16, default 0): the address is then the `n`-th entry from the right of `X-Forwarded-For`, which the nearest trusted proxy wrote, so entries a client forged to the left are ignored; a short or malformed header falls back to the peer. With 0 the header is ignored, because anybody can send it. The server must be served with connect info (`Server::serve` does).
- Passwords, tokens, digests and hashes never reach logs or `Debug` output: `Credentials`, `SessionToken`, `SeatToken`, `TokenDigest` and the stored hash print `<redacted>` or nothing, failed attempts are logged without the name tried, and a test captures every log line at TRACE during a whole sign-up and sign-in and searches it.
- `AuthConfig` (in `ServerConfig::auth`): `registration`, `cookie_secure`, `session_lifetime`, `hash_cost`, `hash_jobs`, `limits`, `trusted_proxies`, `purge_every`; only the first, second and seventh come from the environment. A database failure is 503 `unavailable` without details (logged) and costs no throttle budget.

### Games and accounts
- Migration `20261018000004_seat_users.sql` adds `seats.user_id` (nullable, `ON DELETE SET NULL`), a unique index on `(game_id, user_id)` where it is set (an account holds one seat per game, so "the user's seat here" is one seat) and an index by user. `SeatRecord::user`, `Entry::users` in the registry (bindings mirrored in memory, loaded on boot) and `NewSeat::user` carry it.
- Binding: a signed-in `POST /api/games` binds **seat 0** to the creator, the seat the web opens as "my seat"; guests bind nothing, and a cookie the server does not honour makes the creator a guest instead of an error. The first signed-in join through an unbound seat's link (`/ws/{game}/{token}`) binds that seat to the visitor's account, before the upgrade, if the game is recorded and the account holds no other seat of it. A bound seat never changes hands and a second account never binds to it: `UPDATE seats SET user_id = $3 WHERE .. AND user_id IS NULL AND NOT EXISTS (the user's other seat)` decides, so racing accounts get one winner (`Registry::bind_seat` returns `Binding::{Bound, Already, Taken, Elsewhere, Missing}`; the unique index backs the `NOT EXISTS` up). A failed binding is logged and never stops the join.
- The token stays a bearer secret. Binding adds a way in and a list; it takes nothing away, so old links keep working, no link is rotated or invalidated and a link that was shared on purpose still works. Whoever holds a bound seat's token opens that seat as before (a different signed-in account too: it plays the seat like any guest and is **not** bound, so it can never displace the owner). A seat link is therefore as sensitive as it ever was; what the account gives is rejoining without it.
- Rejoin by session: `GET /ws/{game}` (no token) with the `mtg_session` cookie opens the seat bound to the session's user in that live game; `Join` and everything after it are unchanged (protocol version stays 1). The credential rides on the upgrade request because scripts cannot read an `HttpOnly` cookie and so could never put it into a `Join`; the socket's `Origin` check applies as to the link route. Answers before the upgrade, in the order they are decided: 403 `forbidden_origin`; 404 `not_found` for an address that is not a game id, whoever asks; 503 `accounts_unavailable`; 401 `unauthenticated` (no valid session; a cookie that is no good is cleared); 404 `not_found` again for an unknown game and for a game the user holds no seat in, which are one answer, so a stranger learns nothing about which games exist. Only games alive in the registry can be rejoined: a lobby lives an hour, a finished game ten minutes after the sweep that saw it end.
- `GET /api/me/games` (`MyGames` in `mtg_protocol::rest`) gives `{games: [{game, seat, name, status, created_at, others: [{seat, name, user}], result}]}`: the games the user holds a seat in, lobby, running and finished (expired and failed ones are never listed), newest first, at most 100 (`MAX_LISTED_GAMES`). `seat` and `name` are the user's own; `others` are all other seats in seat order, each with its name and, when an account sits there, its username; `result` is a `GameResult` for finished games and null otherwise; `created_at` is `YYYY-MM-DDTHH:MM:SSZ` in UTC. It reads the database, so a finished game stays listed after the registry dropped it (and can then no longer be rejoined: the list is history for it). 401 `unauthenticated` without a session, 503 `accounts_unavailable` without a database.
- Deleting an account by hand frees its seats and ends its sessions in the database; the running registry still holds the binding in memory until the next restart. There is no delete endpoint yet.

## Tests

## Transport
- `Server::new(config).serve(listener, shutdown)` runs axum; the `mtg-server` binary reads `MTG_BIND` (127.0.0.1:8080), `MTG_ALLOWED_ORIGINS` (comma list), `MTG_MAX_GAMES` (100), the pace of play (`MTG_AUTO_PASS` on; `0`, `off` or `false` turn the default off, `1`, `on`, `true` on, anything else refuses to start; `MTG_RESPONSE_SECS` 10 and `MTG_BLOCK_SECS` 45, whole seconds, `0` for no clock) and, for accounts, `MTG_REGISTRATION`, `MTG_COOKIE_SECURE` and `MTG_TRUSTED_PROXIES` (see Accounts). `ServerConfig::fixed_seed` is for tests only and is never read from the environment.
- REST: `POST /api/games` {format:"normal", seats:[{name, deck}]} gives 201 {game, seats:[{seat, token}]} (2 to 12 seats, 16 KiB `application/json` body, unknown fields refused, the seed is always server-random); `GET /api/games/{id}` gives {started, seats, connected, ready, result} (`ready`: the seats that pressed Ready and did not take it back, none after a restart of a lobby, all once the game runs); `GET /api/decks`; `GET /healthz`; the account endpoints below. Errors are `{error, message}`.
- Every request that changes something (any method but GET, HEAD and OPTIONS) goes through `api::same_site_only`: an `Origin` that is neither in `MTG_ALLOWED_ORIGINS` nor the request's own `Host` is 403 `forbidden_origin`, no `Origin` (a bot) passes. It is the socket's rule (`origin.rs`), applied to POSTs too. CORS answers listed origins only and now sends `Access-Control-Allow-Credentials: true` to them, so a front end on a listed origin may send the session cookie.
- `Registry` holds the games: tokens are 256 random bits from the OS and only their SHA-256 is kept (never logged); a cap on games; a janitor drops finished games after 10 min, lobbies that never started after 1 h and started games nobody has been connected to for 24 h.
- `GET /ws/{game}/{token}`: the token picks the seat before the upgrade (unknown game, malformed id and wrong token share one 404); `Origin` must be listed or match `Host` (no `Origin` is a bot and passes). `GET /ws/{game}` takes the seat from the session cookie instead (see Accounts). Then `Join` within 10 s (wrong version gets `Error{UnsupportedVersion}`, a mismatching game `Error{UnknownGame}`), `handle.join(seat)`, and one text frame per `ClientMessage`/`ServerMessage`.
- Limits per socket: frames at most 64 KiB, a burst of 40 messages then 20 per second, five malformed messages in a row, ping every 20 s and a close after 60 s without a pong. A second socket for a seat replaces the first.
- Close codes: 1001 server stopping or game removed, 1002 bad handshake, 1007 not UTF-8, 1008 policy (rate, malformed run, no join, no pong), 1009 frame too big, 1013 dropped as too slow (reconnect), 4000 replaced by a newer socket of the same seat (do not reconnect on your own). A closed socket drops the seat's queue and never calls `leave`.
- Shutdown (SIGTERM or ctrl-c): stop accepting, send every socket 1001, wait up to 5 s for all of it; a stalled request cannot hold the process.
- Tests (`tests/{ws_games,ws_refusals,ws_limits,rest,registry,shutdown}.rs`, helpers in `tests/net/`) use a real listener on port 0, raw TCP for hostile HTTP and tokio-tungstenite for sockets.
