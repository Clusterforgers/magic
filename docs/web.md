# Web client

The browser client: game creation, lobby, table, decision prompts and accounts, on the wire contract of [protocol.md](protocol.md) and the transport of [server.md](server.md).

## Stack and layout

React, Vite, Tailwind, shadcn/ui on Base UI, TanStack Router and zustand. Commands are in `CLAUDE.md`.

- Pages live in `src/features` (`auth`, `builder`, `create`, `decks`, `game`, `games`, `precons`, `table`); `src/routes` only picks them. The Vite plugin rewrites `routeTree.gen.ts` on `pnpm dev` and `pnpm build`; commit it with the route change.
- `src/net` (REST, socket) and `src/play` (session, store) hold the client. `src/components` has the shell and the pieces pages share; `src/components/ui` is shadcn (`pnpm exec shadcn add <name>`) and is edited to the tokens. `src/protocol` has the ts-rs bindings and the transcripts Rust writes.
- The dev and preview servers proxy `/api` and `/ws` to `MTG_SERVER_URL` (default `http://127.0.0.1:8080`) and keep the browser's `Host`, which the server's Origin check compares with the page's `Origin`.

## Data flow

- `net/api.ts` checks REST bodies at runtime; a failure is an `ApiError` with a code of `crates/mtg-server/src/api.rs` or a local `unknown`, `network` or `bad_response`. `net/parse.ts`: `parseFrame` is the only door from the wire (JSON, known `type`, required fields, 1 MiB cap); garbage is a `FrameError`, never a throw.
- The game browser calls are on the same client (`net/api.ts`): `listLobbies`, `joinGame`, `joinByCode`, `leaveGame`, `releaseSeat`, `setVisibility`, `closeGame` and `chooseDeck` ([server.md](server.md), Game browser endpoints, Choosing a deck). They reject with a `LobbyError {code, status, retryAfter, issues}` whose code is the server's `LobbyErrorCode` or `DeckChoiceErrorCode` (`unknown_deck`, `deck_blocked`, `seat_ready`) or a local `unknown`, `network` or `bad_response`, and `issues` is what a refused deck breaks; `describeLobbyError` (`net/lobbyErrors.ts`) has words for every code, and `net/parseLobbies.ts` reads each body down to its leaves.
  - `listLobbies(previous)` sends the `ETag` of the listing it is given and, on a 304, resolves with that very object, so `result === previous` means nothing changed. A listing carries `fetchedAt`; a row's age now is `age_secs` plus the time since then.
  - A seat token goes in `Authorization: Bearer` and the session cookie rides along, so a call with no token acts for the signed-in user's own seat. `createGame` takes `visibility` and `held` and reads the join `code`.
- `net/socket.ts`: `GameSocket` sends `Join` first and once per connection. `net/pacer.ts` holds sends to a burst of 30, then 15 a second; the server allows 40 and 20 and closes a socket over it with 1008.
- `play/view.ts`: pure ports of `StateView::apply`; unchanged objects, players and zones keep their identity.
- `play/session.ts`: `createSession({game, token, name})` owns the socket, applies the client rule of [protocol.md](protocol.md) and writes the zustand store (`play/store.ts`) that screens read with `useStore(session.store, selector)`.

The session's rules:

- A Snapshot sets the base and `seq`. A batch whose `from_seq` is not `seq` (or any batch but the one at 0 while there is no view) sends one Resync; nothing is applied and decisions are ignored until the next Snapshot.
- A `Decision` replaces `pending`. `answer()` sends once per decision id; a Snapshot or a lost connection forgets answered ids, so the server's repeat can be answered.
- `GameOver` sets `result` and makes a later close final. `StaleDecision` and `IllegalAnswer` give a notice and a Resync; `BadMessage` and `Internal` only a notice.
- A wrong token is a refused upgrade, which a browser reports as 1006, so the client retries forever (`attempt` counts).

| Close or message | Socket status |
|---|---|
| 1001, 1006, 1013 and any code not listed below | `reconnecting`: retry after 250 ms doubling to 15 s, less up to 50 % jitter; a Welcome resets it |
| 4000 | `replaced`, no retry; `connect()` takes the seat back |
| 4001 | `stopped`, no retry, notice "You were removed from this game."; the seat was given back or the host removed the player |
| 4002 | `closed`, no retry, notice "The host closed this game."; the lobby ended, so its links and code open nothing |
| 1000, 1002, 1007, 1008, 1009; `Error` UnsupportedVersion or UnknownGame | `stopped`, reason in `notice` |
| any close after `GameOver` | `stopped`, no notice |

### Card images

- `features/cards/images.ts` (pure): `cardImageUrl(source, face, size)` builds the server's picture URL (`docs/server.md`, Pictures): a printing id when the view has one, else the oracle id, and a token by name, type line, colour letters (`C` for none) and power/toughness. `imageSourceOf(object)` gives none for an ability, an emblem or a card without a record, and the card's source for a token that carries an `identity` (a token that copies a card); `missKeyOf` is a token's URL without power and toughness, the key its miss is kept under; `showsBack` is true for a face-down or hidden card. `imageSizeFor(width)` picks `small` below 110 px drawn width, `normal` below 330 px and `large` above; the fit engine's sizes are unchanged and reach the face through `CardWidthContext` (`CardRow`, `HandFan`).

- `CardImage` is an `<img>` (`loading="lazy"`, `decoding="async"`, the card's 5:7 box and printed corner, 4.75% of the width) over a skeleton, on the table the text face. The skeleton shows while the picture loads and stays for a 404, a 502 or an error, never a broken-image icon; the page remembers loaded pictures and retries a missing one after 5 minutes, except a token's (`missKey`): the server finds a token by name whatever its power and toughness, so a miss holds for the session for every URL of that token, and `children` may be a function of the status. A printing the database lacks (Default Cards holds one printing per card) falls back to the card's picture (`cardImageFallbackUrl`, the oracle endpoint). A picture replaces the skeleton in the frame it loads and never fades, which would show the card half see-through for a moment and every picture does that at once after a reload; one the browser already holds (`img.complete`) is drawn in the first frame. ## Fit and grouping

`features/table/fit.ts` and `group.ts` are pure (no DOM, no store) and decide how big a zone's cards are and which permanents share a box.

- `fitRows(box, groups, limits)`: `box` is the zone's width and height in px; a group is a row with its `stacks` and its card shape (`aspect` 7/5; `scale` of the zone's card width, 1, or `LAND_SCALE` 0.8 for lands). It tries card widths from 112 px down to the 44 px floor in steps of 2 and answers with the first at which every row wraps inside the width and all lines fit the height. A width that fits keeps fitting at a smaller one, so a bigger box never gives a smaller card.
- Whole pixels: the box is floored; a row's box is the card width times `scale`, rounded to the nearest px (halves up), and its height that width times `aspect`, rounded the same way. `layout` carries each row's box, `perLine` and `lines`; components draw exactly those sizes. Every stack takes one box of its row's size, tapped or not. `FIT_LIMITS` puts 6 px between boxes and 4 between lines, wrapped or of different rows; a box narrower than one card still takes one card a line.
- When the floor does not fit the height, `scrolls` is true at the floor and `hidden` counts the stacks on lines cut off at the bottom of the box, the "+N" of the zone's edge fade. `rows` and `lines` count the rows with stacks and all wrapped lines.
- `groupPermanents(permanents, { groupOthers })` merges permanents with the same face into a `Stack` (`key`, `count`, `members`): name, owner, controller, token or card, types, colors, power, toughness, abilities, tapped, summoning sick, damage, counters, attachments and the host it is attached to. Tapped and untapped never share a stack. Lands and tokens always merge; other cards only with `groupOthers`, which the caller sets when a zone's fit is under `GROUP_OTHERS_BELOW` (64 px).
- Attachments ([ui-design.md](ui-design.md#attachments)): an attachment whose host is on the battlefield takes no box; it is a `tucked` id of its host's entry (`tuckedOf`: Auras, then Equipment, then Fortifications), drawn behind the host with its name line above it, and `LaneCounts.tucked` gives `fitLanes` the deepest tuck of each lane, which adds `depth × tuck` px to each of its lines (`tuckOf`).
- Stacks come in the order of their first member. A merged stack's key is its face and a card that stays alone has its id, so a key survives members joining and leaving, and one member joining or leaving changes no other stack's key, count or place. `expandStack(stack)` returns the members, for opening a stack in place and for prompts that need each one; regrouping them gives the same stacks.
- Use: `battlefieldStacks(state, seat)` (`rowStacks.ts`) groups a seat's rows once per view into ids and keys, twice: lands and tokens merged, and every identical card merged too. `layoutSeat` fits the zone's content box (`useContentBox`, a `ResizeObserver`) with `fitLanes` (`laneFit.ts`, below) over the first and, when its cards would fall under `GROUP_OTHERS_BELOW`, over the second: one box per stack, one per member of an open stack, lands at 0.8. It returns each lane's entries (`ids`, `open`, `held`, `tucked`) and the `LaneFit`; the lanes draw exactly those boxes, a tapped one included. A permanent in combat (`role`) never merges, so its marks and lines stay its own. `Battlefield` draws the bands of the fit and writes `--card-w` and `--card-h` and the width on each lane; a face is whole from 76 px, short below it and takes the larger type from 150 px. Without a measured size (jsdom, a hidden zone) cards keep the box of their size. `CardRow` takes the box (`box`) and, for the hand, the gap (`gap`, negative to overlap). `fitPerf.test.ts` holds grouping and fitting 40 permanents a seat for 6 and 12 seats to a few milliseconds.
- `fitLanes(box, counts, facing, limits)` (`laneFit.ts`, pure): the lanes of a board are lands, creatures and other permanents (`rowOf`: a creature of any other type is a creature; artifacts, enchantments, Backgrounds, planeswalkers and battles are other permanents). A shape stacks them in bands: `one` (lands, creatures, other side by side), `two` (creatures, then lands beside other permanents) or `three` (a band each); bands run from the middle of the table outwards, so an opponent's (`far`) are reversed. A band takes the fewest lines at which its lanes fit the width side by side, every lane of it with that many lines. Creatures take the card width, lands and other permanents 0.8 of it (`scaleOf`), so creatures are the largest cards on a board. A band with lands may instead fan them (`fanLane`): the lands in the most piles that fit beside the other lanes in one line, each land lying over the one before it below its head (14 % of its height, at least 20 px: the name line); the fan wins only where it is lower than plain lines, so it is taken exactly where it buys a larger card. `CardRow` draws a fan as a grid of columns whose rows are the heads and a last card-high row, a land the keyboard focuses coming to the front (not a hovered one, which would cover the head of the next). For each shape a binary search over the ladder of `LANE_LIMITS` (224 px down to 44 in steps of 2; 6 px between boxes, 4 between lines, 12 between lanes and between bands) finds the largest card at which all bands fit the height; the largest wins, a tie going to `two`, then `one`. A fitting width keeps fitting at a smaller one, so a bigger box or fewer permanents never give a smaller card. Without a fit at the floor the shape that needs the least height scrolls, creatures first on every board, and `hidden` counts the boxes cut off. An empty lane has no place in any band and takes no room.

## Prompts

`features/table/prompt/` answers the decision this seat faces.

- `PromptHost` (in `SharedStrip`, in place of the read-only "Waiting for ..." line while `ownDecision` is set) renders `PROMPTS[kind]` with the kind's `options` in a scope keyed by decision id, so a new decision remounts the prompt with an empty selection.
- `registry.ts` has an entry per `DecisionKind`; a new kind stops compiling until it has one (`kinds/<Kind>.tsx`, a `PromptComponent<'Kind'>` with props `{ options }`). `kinds.test.tsx` fails while one of the nineteen built kinds (the eight the table has always asked, `ChooseTargets`, `OrderTriggers`, `YesNo`, `ChooseOption`, `ChooseMode`, `ChooseCards`, `OrderCards`, `ChooseNumber`, `ChooseReplacement`, `DivideAmount` and `ChooseCosts`) is the `UnsupportedPrompt` stand-in. `UnsupportedPrompt` is the generic prompt (the last bullet of this section); `PromptHost` also draws it for a decision whose key is no kind of `PROMPTS` (a server newer than the client), with the key as the decision's name.
- `usePrompt()` gives `{ id, name, decision, answer, selection }`. `answer(a)` wraps `session.answer`: once per decision, false when already sent, refused by the socket (a retry is allowed) or when the store holds another decision by now. `PromptLayout` (prop `text`, controls as children) draws the shared shape: the decision's name, one polite live sentence, a row of controls.
- Card marks (`prompt/marks.ts`): `useCardMarks(marks, onSelect, { toggles })` takes a `Map<ObjectId, 'legal' | 'dimmed' | 'selected'>` from `markCards(own, legal, selected)`. A click or Enter/Space on a legal or selected card calls `onSelect(id)`; a `Card`'s own `highlight` and `onSelect` props win. Each `Card` subscribes to its own id, so publishing redraws only the changed cards.

## Combat overlay and previews

`features/table/combat/` draws what combat will do from the engine's `combat_forecast` in the table view ([engine.md](engine.md), [protocol.md](protocol.md)); `net/parse.ts` checks it down to its leaves. The client never works an outcome out: it shows the engine's numbers and hides them when they cannot hold.

- The seam: `useBlockPreview()` (`forecast.ts`) is the forecast to draw; the overlay, the marks, the key, the sentences and the prompts' outcome all ask it. It is the table's forecast while no choice is pending and the engine's preview of the choice being made otherwise (`previewFor`, a pure rule), because the table's forecast describes combat as it stands. A forecast is never drawn for a choice it does not describe: marks go the moment the choice changes and return with the reply.
- `CombatOverlay` is an SVG over the table column (`aria-hidden`, `pointer-events: none`, mounted only while a line exists) in two layers: the lines under the centre strip and a faint copy above it, so a line behind the prompt can still be followed. `plan.ts` (pure) turns the combat view, forecast and unsent choices into lines: attacker to seat or planeswalker (muted), blocker to attacker (strong, coloured by the pair's outcome), unsent choices dashed.
- `rects.ts` measures the DOM when anchors appear and, once per frame, when something may have moved, never per render (`shapesOf` bows a block line to the other side of its travel than an attack line, so the lines of a fight bow the same way on the screen, clear of the pod column at the left); jsdom has no layout, so tests inject a `RectProvider`. A card that a clipping or scrolling ancestor cuts off entirely (a board squeezed to no room, a card scrolled out of its zone) is not drawn, so its line runs from and to its controller's pod or tile instead of to where the hidden card lies in the page; `fit.spec.ts` holds that no combat line runs over your life.
- Marks: `data-doomed` and a "Dies" badge, a "-N" badge for damage, and on an attacked seat a chip in its life area (`LifeForecast`, `data-slot="life-forecast"`): the change of life in red ("-3"), in green when a lifelink blocker would more than make up for it ("+2"), "0" when all is blocked, a skull on a filled chip when lethal; it takes no row of the pod, is named by "Life would go from 20 to 17" and its tooltip adds the forecast's sentences. The forecast lists attacked seats only, so the life an attacker's controller would gain shows nowhere. The key (`CombatLegend`) lists only the kinds of line on screen.
- DeclareBlockers publishes its pairs and DeclareAttackers the attack so far (`usePublishPending`, `pending.ts`). Both end with `prompt/PreviewOutcome.tsx` (`data-state` `checking`, `ready` or `unavailable`) as visually hidden parts, for a screen reader: the engine's sentences, "Checking outcome…" or "Outcome shown after you confirm."; the eye gets the chip of the seat and its tooltip.
- Preview ([protocol.md](protocol.md), Preview): `session.preview(decision, answer)` sends one `Preview` for the pending decision and remembers the answer's key (`previewKey`, the answer as JSON, so order of choice counts). Replies come in order, so the client keeps only the newest question's as `store.preview = { decision, key, forecast } | null`, dropped with the decision, a snapshot, game over and the connection. An `Error{BadMessage}` while a preview is unanswered means an older server does not know previews: no notice, and none are asked again until the next connection.
- `usePreviewRequest(decision, answer)` asks `DEBOUNCE_MS` (80 ms) after the choice last changed, so a run of clicks asks once, and returns `idle`, `checking`, `ready` or `unavailable` (no forecast, a session that would not send, or `GIVE_UP_MS`, 1.5 s, without a reply). Prompts pass the answer Confirm would send (`blocksAnswer`, `attacksAnswer`, also used by the seam), so the question's key is the choice's key.

## Table feedback

`features/table/fx/` draws short animations for what a batch did. They decorate the true state, which the table already shows when they start: nothing waits for them, no answer is delayed, and ending one only removes an attribute.

- `watchBatches(store, fx)` (`batch.ts`) subscribes to the play store. `batchBetween(prev, next)` takes a change for a batch only when `seq` moved on by exactly the events appended to the log, so snapshots (told apart by `PlayState.snapshots`, since one may bring the log it spans), decisions and chat never animate. `deriveEffects(before, after, events)` (`derive.ts`, pure) returns `Effect[]` in a fixed order (life by seat, then `attacked`, `blocked`, `damaged`, `entered`, `died`, each by object id) and reads the object diff off the two moments, since the fold keeps the identity of every unchanged object.

| Effect | Comes from | ms |
|---|---|---|
| `attacked`, `blocked` | `AttackersDeclared`, `BlockersDeclared` and the combat diff | 500 |
| `damaged` | a permanent: `DamageDealt`, else newly marked damage; a seat: the life diff, since no event says life | 550 |
| `healed` | a seat: the life diff | 550 |
| `entered` | a permanent that was not on the battlefield | 350 |
| `died` | battlefield to graveyard, or named by `CreatureDied` (a token); at most 24 a batch | 500 |

- A `died` effect carries the card's last look, so a ghost stands where it was; a player who loses takes their permanents out of the game, so they vanish without ghosts.
- `createFx(options)` (`store.ts`) keys effects by card, seat and battlefield row; `FxState` is replaced, never changed, so an untouched card keeps its snapshot. One timer per kind and batch removes effects after `FX_MS`; a batch plays at most 120. `mode` (`off`, `reduced`, `full`) is read at every batch; `reduced`, while the system asks for less motion, plays only still highlights.
- `TableOptions.effects` is on by default except under vitest (`import.meta.env.MODE === 'test'`), so other tests see no timers and no extra markup; a test turns it on with `renderTable({ options: { effects: true } })` and `vi.useFakeTimers()`.
- `Card` sets `data-fx` and `data-fx-side` (`own` or `other`), `LifeFx` wraps the life figure, and `CardRow` puts each `GhostCard` back before the card it stood before, as an `aria-hidden` `li` with no `data-object-id` and nothing focusable.
- Durations are the custom properties `--fx-<kind>-ms` in `fx/fx.css`, which `fxCss.test.ts` holds equal to `FX_MS`; `--fx-slow` stretches them.
- `fx.travel` (`travel.ts`, `places.ts`, `FxTravel.tsx`) flies the moves of `deriveMoves` with the Web Animations API on a fixed `aria-hidden` layer without a pointer (`.fx-travel`, outside the layout): `watchBatches` calls `launch`, which measures each source at once and each destination on the next frame (`measurePlace`: the card, else the anchor of its zone, else the move is left out); `planFlights` staggers the legs by `MOVE_MS.stagger`, the second leg of one card starting when its first has landed, and `keyframesOf` runs a straight path, whole halfway, inside the window, fading as it lands. A card the viewer may not identify flies as a back and turns face up as it reaches the stack; an ability flies as a chip. Nothing flies under `reduced` or `off`, and a batch with moves ends the flights of the one before.
- Moves from a zone to the stack and on, the spotlight, target arrows and the hand's reasons: [ui-design.md](ui-design.md), Playing is legible.
- Stack targets: `stackTargets.ts` (pure) lists each stack item's targets once with `gone` read from the player's `lost`, the view and the log since the cast (`movedSince`), `stackText.ts` words them (chip line, label), `combat/stackArrows.ts` plans the arrows as `LineSpec`s of kind `target` from a `stack` anchor (`data-stack-chip` on the chip) that `CombatOverlay` draws in its `stack` layer; the item on show is `usePreviewTarget` when it is on the stack, else the top.
- Log wording that needs the events around a line (`eventContext.ts`): the resolving spell ("X counters Y", "Y is exiled by X") and the targets of an activation, passed to `describeEvent` by `foldLog` and the turn ticker.

## Pace controls

The Priority prompt's controls (`prompt/PassControls.tsx`, drawn in the controls dock of the table, 44 px high), over the wire rules in [protocol.md](protocol.md) (Pace of play) and the design in [arena-flow.md](arena-flow.md).

### Primary button and yields

`data-slot="primary-action"` answers `Pass` (disabled when `can_pass` is false). `primaryLabel` (`passWords.ts`) is display only; the server decides what happens. "Pass priority" is never a visible label; it is the `aria-description`.

| Situation | Label |
|---|---|
| a spell on the stack | "Resolve <top spell>" ("Resolve" in a short dock) |
| the viewer's turn, before the last window | "Next: <next step>" ("Next: Combat"; "Next: Attackers", "Next: End combat", "Next: Main 2" in a short dock) |
| the viewer's turn, the End step | "End turn" |
| another seat's turn | "Continue" |

The dock's form (`DockForm`, `dockForm(regions)` in `layout.ts`, `ControlsSlotProvider form`) decides how much these words say: `full` (a main area of 1161 px or more, `DOCK_FULL_MIN_MAIN_PX`: the least width at which an opening hand and two commanders keep one hand row beside the widest dock, from `handRowPx`) draws the key hints (`data-slot="key-cap"`) and the whole words; `short` (any other window above a phone) leaves the hints to the tooltips, `aria-keyshortcuts` and the menu's legend, writes the short words, which keep the dock under 300 px (`primaryLabel(situation, form)`; the spell's name is the top chip of the stack strip and in the description a screen reader hears), and trims the buttons to `px-3`; `compact` is the phone's dock.

- "End turn" (`data-slot="secondary-action"`; not drawn when the primary button already ends the turn, and in a phone's dock it is the first item of the menu) asks for `yieldUntil('EndOfTurn')`. The menu "More ways to pass" has "Resolve everything on the stack" (`Resolve`, only over a stack) and "Pass until my next turn" (`MyTurn`).
- A yield is asked once per prompt: the buttons stay off until the server answers with `Yielding` (the prompt goes) or a fresh decision (the yield ended at once). The server refuses a yield under Full Control, so there `yieldUntil` sends nothing and the prompt draws neither "End turn" nor the menu.
- `YieldIndicator` ("Passing until the end of turn", with "Stop passing" for `cancelYield()`) shows while the store's `yielding` is set; only `Welcome` and `Yielding` set it. A `Priority` decision on screen is cleared when a yield starts or, for a yield that ended inside one step and was never told, with the next batch.

### Stops and Full Control

`features/table/stops/` and `play/session.ts`. The server decides the windows from the stops and the mode ([protocol.md](protocol.md), Stops and Full Control); the page only asks for them and shows what the server holds.

- `stops` (`{side, step, keep}`; `keep` true is lasting, false goes once its step has passed) and `fullControl` (`Off`, `NextWindow`, `Held`) are replaced whole by `Welcome`, `Stops` and `FullControl` and survive a dropped connection until the next `Welcome`.
- `StopLadder` (in `StopsBar`, beside `FullControlToggle`) draws one row with a button per step in turn order (ten; first-strike damage joins while it is the current step or holds a stop) and `StopSideSwitch`, "Mine" (your turns) or "Theirs" (opponents'), which picks the side on show. The row follows the turn and a side picked by hand holds until the turn changes hands; the side out of sight shows its count on its segment. Both rows stay in the page, one `hidden`. Untap and cleanup get none: the server refuses them, so `setStop` sends nothing for them (`play/stops.ts`). A lit button (`aria-pressed`) is a stop the server holds; `data-keep` is `turn` or `lasting`.
- `StopsDock` puts `StopsBar` in the controls dock as one row from 1600 px, else behind the "Stops" button (named "Stops, 2 set, Full Control held"). The popover (`layout="panel"`: the steps in a grid of five, Keep labelled) stays in the page while shut, so the Keep toggle, the side picked and the Control keys keep working.
- A press sets a one-turn stop and clears a held one; shift and press, or the Keep toggle (for touch), sets a lasting stop and makes a one-turn stop lasting (`pressRequest`). The toggle asks for Held, or Off when a mode is on; its menu asks for the mode it names.

### Response clock

- A `Decision` with `deadline_ms` ([protocol.md](protocol.md), Decisions) becomes `pending.deadlineMs`. The session counts it down in `PlayState.clock` on its own `timers` (a test's manual clock moves it) and, at zero, clears `pending` itself: the server has answered for the seat, and a prompt left up would invite a stale answer.
- `prompt/ResponseClock` shows "Passing for you in 7 s" (`clockText.ts` has the words for what the server answers at zero: a pass, no blocks, no targets, the triggers in the order they triggered, No, the first option, the first mode, or the cast cancelled when `can_cancel` allows it, the first cards of a list or none when `min` is 0, the order kept; `clockKind` tells those choices of modes and cards apart) as a `role="timer"` that does not announce each second; the last three seconds are urgent (`data-urgent`). Its bar is the `response-clock-bar` utility in `prompt/responseClock.css`.

|---|---|

## Accounts and games pages

Sign-in uses the server's accounts ([server.md](server.md); bodies in [protocol.md](protocol.md), REST bodies). A guest needs no account: a seat link opens a seat. A server without `DATABASE_URL` answers 503 `accounts_unavailable`, and the app then offers no sign-in anywhere.

- `net/accounts.ts` `createAccountsApi({fetch, baseUrl})` sends `credentials: 'include'`, as `api.createGame` does, which binds seat 0 to the creator. A failure is an `AccountError {code, status, retryAfter}` with the server's `AuthErrorCode` or a local `unknown`, `network` or `bad_response`; `AUTH_ERROR_CODES` is a `Record` over the generated union, so a new code stops the build until it has words.
- `features/auth/store.ts` `createAuthStore({api, initial})` is the app's `appAuth`, started once by `AuthProvider`; a page without a provider (most tests) gets a stand-in whose status is `unavailable`. `status` is `loading` until `GET /api/auth/me` answers, then `signed-in` (200), `signed-out` (401, and a network, 5xx or unreadable answer, since nothing is then known to be signed in) or `unavailable` (503).
  - A failed `logout` keeps the user and sets `notice`, since a cookie that is still alive must not look signed out. An answer that arrives after who is signed in changed, or after a newer question, is dropped (`round` counter).

- `/login` and `/register` (`AuthScreen`, `AuthForm`) are a card in the `narrow` column: the title, one line of purpose, the form and a footer link to the other page that keeps `next`. They check a username of 3 to 32 letters, digits, `_` and `-` and a password of 10 to 128 characters (`rules.ts`, copies of the Rust constants) before sending. The password is in no React state: the field is uncontrolled, read at submit, sent, and emptied once the answer is in, except after a taken username on `/register`, where it stays so the player changes the name only. Every `AuthErrorCode` has a sentence and a field (`errors.ts`; a wrong sign-in names neither half).
  - A field is its label, its rule (`USERNAME_RULE`, `PASSWORD_RULE`), the input and, under the input, the problem. A problem has an icon and its words and sits in a polite live region that is always in the page and first in the input's `aria-describedby`, so a screen reader hears it while focus stays on the field; focus goes to the first wrong field. A failure of the whole form is an `Alert` with an icon, a title ("Could not sign in", "Could not create the account") and the sentence, and takes focus. A server with no accounts is an `EmptyState`. The tab order is username, password, the button, the link.

- `next`: `sanitizeNext` (`features/auth/next.ts`) accepts only a path on this site: one leading `/`, no backslash or control character (a tab inside `/<tab>/host` is deleted by URL parsing and gives `//host`), no `//` after dot segments, not `/login` or `/register`, and no fragment, because a seat token must not travel in a query string. `parseAuthSearch` always names the key (`next: undefined` when refused): the router merges what a route validates over the raw address, so leaving the key out would let the unchecked value through.

- `/precons` (`features/precons/PreconsPage`): the precon browser, public like the card endpoints. `net/precons.ts` `createPreconsApi({fetch, baseUrl})` is the typed client of `GET /api/precons` and `GET /api/precons/{code}`; a failure is a `PreconError {code, status, retryAfter}` with the server's `PreconErrorCode` or a local `unknown`, `network` or `bad_response` (`errors.ts` has words for each, and a 429 names its wait; 503 `cards_unavailable` shows "No card data on this server" with no Retry). The page is `wide` and fits the window under the header like Play: the title with a count status, `PreconFilters` (a search over name, set code and commanders that ignores case and accents and matches every word; a set menu with each set's count, newest first; a deck-check menu) and the rows in a region that scrolls inside the page. `PreconRows` draws a table from 64 rem (Deck, Set with its release month, Commanders, Cards, Deck check, Action) and stacked rows under it; both carry `data-precon` and `data-status`.
  - The badge (`PreconBadge`, an icon and words over `DeckStateBadge`) follows `statusOf`: "Whole deck runs" (`verified`), "N cards played by hand" (partial, manual and stale copies: `manual_play`) or "Cannot be taken" (`blocked`, or `playable` false). A deck the game cannot take keeps its Play in place, `aria-disabled` and described by the badge, with the line "Details list what stops it."
  - Details (`PreconDialog`, `usePreconDetail`): the list's own facts show at once, the cards of `GET /api/precons/{code}` follow. A deck that cannot be taken shows the server's `issues` in an alert, or says it holds cards the game cannot play. Each board (Commander, Main deck, Sideboard) lists its cards with a `SupportMark` and, for a card that is not Verified, "Played by hand:" and each clause as the words of the card it covers beside the reason (`ClauseList`, the same as the not-validated list), or the state's words when it has none. A switch narrows the list to those cards, and "Copy list" copies the cards that are not Verified as blocks (`copyList`, in board order, the precon as the deck), with the quotes once their texts are read (a disabled "Reading card text…" until then). A view that was read stays for the life of the page, since the server counts every request against a budget per address. The words come from `GET /api/cards/{oracle_id}` (`useCardTexts`; `PreconsPage` takes the card client as `cards`), because the precon view carries the clause spans and reasons but not the text.
  - Play (`usePlayPrecon`, `play.ts`): `createGame` with the create form's defaults (two seats, listed, only seat 1 held) and `deck: "precon:<code>"` for seat 1. `format` is `commander` for a deck the check judged as Commander and `normal` for any other. A signed-in visitor plays as the account in one click; a guest answers `GuestJoinDialog` ("Play <name>"), a name kept in `localStorage`. Success opens the lobby on seat 1 (`/game/$gameId#seat=0&token=…`) and keeps the invite link and code as the create form does. A 422 or `unknown_deck` is the precon's own trouble: the page shows "Could not start a game with <name>" with Show why (the details) and Dismiss. A failure that sending again could fix (offline, a busy server) stays in the guest's dialog.

- `/games` (`features/games/MyGamesPage`): signed out goes to `/login?next=/games`. The page is `wide` and fits the window under the header like Play: the title with Create game, a count line (a polite status) with Refresh, then the rows in a region named "Your games" that scrolls inside the page (it is `relative`, so the screen-reader words of a row scroll with it instead of lengthening the page). `GameRows` draws a table from 64 rem (Players, State, Result, Your seat, Started, Action) and stacked rows under it; both carry `data-game` and `data-status`. Players names the other seats by username or seat name, and seats nobody has taken read "an open seat" or "3 open seats" (`othersText`). State is a badge with a word (Lobby, Running, Finished, Failed) and Result reads "You won", "Bo won", "Draw" or "Ended without a result".
  - "Continue", a link named "Continue your game with Bo", opens `/game/<id>` with no fragment, which connects through the session. A finished game has none: the server drops it from memory ten minutes after it ends, so the row is the record.
  - A game that failed to resume (`status` `failed`) has a warning badge "Failed", the server's `reason` in the Result place (a sentence in a measure of its own, `resultText`) and no link: its action is "Remove", a button named "Remove your failed game with Bo" that is busy while the request runs. `removeGame` in the store sends `DELETE /api/me/games/{id}` and drops the row, or loads the list again on a 404; a failed removal keeps the row under an `Alert` "Could not remove the game".

- `/settings` (`features/settings/SettingsPage`, linked as "Account settings" in the account menu): signed out goes to `/login?next=/settings`; a server without accounts shows an empty state. The page is a `narrow` column with two cards that use `Field` (`features/auth/Field`, the label, rule, input and live problem of the sign-in forms). `ChangePasswordForm` has the current password, the new one with `PASSWORD_RULE` and the new one again; it checks that the current one is typed, the new one follows `passwordProblem` and the two match, sends `changePassword(current, new)` once, empties the current password after every try (the new ones after a success), puts a wrong current password on its field (`describeAccountError(error, 'password')` gives it field `current`) and a rejected new one on the new field, and announces "Password changed" in a status that is always in the page; the account stays signed in, the server ends its other sessions. `DeleteAccountSection` explains what goes and opens an alert dialog that asks for the password; a wrong one or a refusal keeps the dialog up with the reason, success shows the flash "Your account was deleted." and goes home, signed out (`onDeleting` keeps the page from redirecting to the sign-in form on its way). `net/accounts.ts` has `changePassword` and `deleteAccount`; the store actions of the same names return a `SettingsResult` and turn `unauthenticated` into signed out.

- `/decks` (`features/decks/DecksPage`): signed out goes to `/login?next=/decks`. `net/decks.ts` `createDecksApi({fetch, baseUrl})` is the typed client of the deck endpoints; a failure is a `DeckError {code, status}` with the server's `DeckErrorCode` or a local `unknown`, `network` or `bad_response`, and 503 `decks_unavailable` shows a notice in place of the list. A row (`DeckRow`) shows name, format, card count and the marker beside the name (`DeckMarker`: a pill with an icon and a word, Verified, Manual play, Blocked or Unchecked, or "Changed since the last check" when the stored check is stale) over one line that says what the state means for the deck (`checkNote`: "96 of 100 verified, 4 played by hand"; for a blocked deck its issues and "Cannot be taken to a game until its issues are fixed", the words (`BLOCKED_MEANING`) the Blocked badge carries as its hover too). Export links to `GET /api/decks/{id}/export` in three formats; Delete asks first. New deck saves a name and a format; Import reads a pasted list or a file, names its check before it is saved (`ImportCheck`: the state badge and "19 of 26 verified, 7 played by hand" from `POST /api/decks/check` with the lines read, and the rules of its format it breaks; "The deck is checked when it is saved." when the check does not answer), lists what it ignored or could not find, and saves the cards under a name. From `sm` up the page is as tall as the window under the header and only the list scrolls. Each row links to the builder, and New deck and a saved import open it. A row lists the deck's commanders, a partner or Background too, each as a picture and a name (`commanders` of the list item, `DeckRow`). "Not validated cards" in the header opens `/decks/unvalidated`, and a row whose check found a card that is not Verified links to `/decks/$deckId/unvalidated` in the words of the count (`unvalidatedLink`, "Show the 7 cards played by hand").

The deck pane edits a draft of pure functions (`deckEdit.ts`: one line per card and zone, at most 250 cards): plus, minus (the last copy removes the line), remove, move one or all copies to another zone, name and format. Save (in the save bar, below) sends the whole deck and shows the report the server answers. The router asks before a navigation away (`useUnsavedGuard`, `LeaveDialog`) and the browser before a reload. From `sm` up the page is as tall as the window under the header and the two panes scroll inside their own regions; under `lg` a Show switch (Search, Deck, Stats) shows one pane, the Deck for a deck with cards (`openingPane`) and the Search for an empty one; from `lg` the two panes share the width 5 to 7 in favour of the deck.

- The deck check in the builder (`report.ts`, pure) reads a `DeckReport`: a counts line from `summary.counts`; every line whose card is not Verified gets a `SupportMark` (icon, word and a left edge in the state's colour, tokens `support-*` in both themes) and the report's reasons as plain sentences, naming the face when a clause is not on the front; Issues only and a sort by name or issues first (unplayable, manual, stale, partial) work within each zone; `report.legality` is a section of its own above the zones and holds no support mark. A card the report does not list keeps the state its search result carried and has no reasons. The marker beside the name (`DeckMarker`) is the state's badge, or "Changed since the last check" while the draft differs from the saved deck, with "Unsaved changes" beside it.

The counts, marks, reasons and legality section follow the report that comes back. Until then the saved report shows with "as saved" and "Checking…" on the counts line, and a later change keeps the last report on screen while it is checked again. A failed check keeps the last report and says so with Try again, which asks at once. The saved report returns the moment the draft is the saved list again.

- The deck pane (`DeckPane`) draws the cards as pictures or as the dense text list (`LookToggle`, "Show cards as"; `deckLook.ts` keeps the choice in `localStorage`, pictures by default). Pictures (`PictureZone`, `CardTile`) group each zone by type with the shared `groupByKind` order (`groupLines` of `deckSummary.ts`: by mana value and name, or as given for the issues sort), each group headed by its copies; a tile is the picture (9 rem or more wide, `normal` size), a `×N` badge, the name that opens the card preview, the state's mark and ring for a card that is not Verified, a note for a card outside the commanders' identity, minus and plus, and a menu to move or remove. The list rows and the tiles share `Copies` and `MoveMenu` (`LineControls.tsx`), so every control keeps its name. The header says how many cards are played by hand (`handSentence`: "7 cards played by hand, 1 cannot be played", a button that opens the list) over the check's counts, the look, Issues only and the sort. The body holds the commander slot (pictures of 112 px), the legality issues, two disclosures and the zones. "Stats" (`StatsPanel`, closed with "20 lands, 8 spells" beside it) is the shared `SupportBar`, `ManaCurve` and `TypeBars` of `features/decks/preview`, the deck's colour identity, `ColourCounts` (spells by colour identity, lands left out) and the land count over the draft (`previewFromDraft`). "Played by hand" (`HandList`, `handCards`) lists each card that is not Verified once with its copies, picture, mark, reasons and flag, worst state first, the cards the game cannot play under "Cannot be played". The save bar (`SaveBar`, `saveStatus`, sticky at the foot of the pane) says "All changes saved.", "Unsaved changes." (with the legality issues, which never stop a save), "Saving…" or "Cannot save yet. <name problem>", and describes Save. Under `lg` the Stats part of the switch shows the header, both disclosures opened and the save bar.
- The commander slot (`CommanderSlot`, in the deck pane header of a Commander deck; any other format lists the command zone as a zone): one commander or two, each a picture, name, type line and identity discs, with a Remove button; an empty slot says what may go there and starts the search for it ("Find a commander" sets the type filter to legendary creature, "Find a partner" and "Find a Background" the text and type). A card enters the command zone only after `judgeCommander` (`commanderCheck.ts`) sent the zone with the candidate to `POST /api/decks/check` and the report named no `commander_count`, `commander_eligibility` or `commander_pair` issue, so the pairing rules (a legendary creature or a card that says it can, Partner, Friends forever, Doctor's companion, Choose a Background) live in the server alone; a refusal shows above both panes with the issue's sentence and Dismiss, a card that already leads the deck is refused at once, and a failed check refuses too. The menu of a search hit and "To commander" of a deck line go through the same check (one copy moves). The commanders' colour identity (`identity.ts`, the union of the cards' `color_identity`, which the server takes from Scryfall so hybrid and Phyrexian symbols count and devoid does not matter) feeds a "Commander's colours" switch in the filters (the `identity` search parameter; `C` for a colourless commander), a note "Outside identity: Red" on a hit outside it, and the slot's count of cards outside it; the report's `color_identity` issue marks its deck line and sorts it first under Issues only.
- The card preview (`CardPreview`) opens from the name of a deck line or a search result: a dialog from `sm` up, a sheet from the bottom under it; Escape or Close shuts it and focus returns to the name. A card (`UnvalidatedCard`) shows its picture (`CardPicture`), name, `SupportMark`, its decks as links and each clause (`ClauseList`): the words of the card the span covers, quoted, beside the plain reason; a card with no clause of its own shows its whole text and the state's words. "Copy as text" copies the cards shown (`copyText`), one block each: `Card Name (Manual) - decks: A, B`, then `  - "<span>": <reason>` per clause (the reason alone when the text is unknown; lines of the card joined with " / "). It waits, as a disabled "Reading card text…", until every card is read.

- The create page waits until it is known who is signed in; a signed-in creator gets seat 1 named after the account. The lobby shows "signed in as" on seats with an account (`useSeatAccounts`).
- Game page: with a seat link, `GamePage` joins by token whoever is signed in (the server binds an unbound seat to the signed-in visitor). Without one and signed in, `GamePage account=<username>` opens `/ws/{game}` (no `GameSocketOptions.token`) and the cookie of the upgrade picks the seat; `Join` carries the username (the server ignores `name`). `ConnectionNotice` words this session connection (`via="session"`).

## Testing

- vitest on jsdom: `scripts/check.sh web`, or `pnpm test` in `web/`.
- Clock budgets and timeouts (the vitest test and hook timeouts, `asyncUtilTimeout`, explicit `waitFor` timeouts, the time budgets of `perf.test.tsx` and `fitPerf.test.ts`) go through `scaled(ms)` (`test-utils/loadFactor.ts`): times `1 + load / cores` (one-minute load average), at most `MAX_LOAD_FACTOR` (12). `MTG_LOAD_FACTOR` sets the factor; `MTG_STRICT_PERF=1` keeps the numbers as written.
- A test of a timer (a pause, a debounce, an animation timeout, a polling interval) never sleeps or races the real clock: it runs on a fake clock (`installFakeClock` in `test-utils/fakeClock.ts`, with `settle(ms)` to let time pass; `renderBuilder` hands such a test a user-event that follows it) or waits with `waitFor`/`findBy` on the state it asserts. `flushFakeClock` ends a fake clock by running the timers still pending, so a menu's teardown is not left for the next test.
- `src/test-utils` has the fakes (`FakeNetwork`, `FakeTimers`, `startSession()`), the Rust-generated `transcripts` (replayed through the real store by `transcript.test.tsx`) and the harnesses: `renderGame()` (fake sockets, manual clock, in-memory REST), `renderTable` and `renderLiveTable` (they lay the table out for `TEST_VIEWPORT`, 1600x1000, which has the side column and the whole controls dock; `options.viewport` sets another, and jsdom has no layout, so a test that needs measured sizes fakes `ResizeObserver` and `clientWidth`, as `zoneFit.test.tsx` does), and `renderApp(url, {accounts, rest})` with `startAccounts(script)`, an in-memory account server.
- `renderGame({ routed: true })` mounts the game page at its own address with a stand-in for Play at `/`, so a test sees where Close and Leave lead (`h.router`) and the notice there. `test-utils/lobbyControls.ts` has `openLobby` (a host or guest lobby with its roster pushed), `changesOf` (the `PATCH`, `DELETE`, leave and release the page sent, with their bearer token), `held` (an answer a test lets go of when it chooses) and the server's `FAILURES`.
- `test-utils/passControls.ts` finds the primary button by its slot, since its words change. A new prompt copies `Priority.test.tsx` (table-driven) and `PriorityLive.test.tsx` (real session, one Answer per decision).
- Screenshots: `node scripts/ui-shot.mjs <url> <out-prefix>` (options in `CLAUDE.md`) over a dev route. The page loads at the first width, so shoot one width per run: state read at mount does not follow a later width. The table follows `resize`, so one run may shoot several widths.
- Layout audit: `node scripts/ui-audit.mjs <url or /path>... --base <dev server>` measures pages in Chromium (`CHROMIUM_PATH` as for e2e) with the rules of `layout.spec.ts` and prints a row per page, size and theme; it exits 1 when a row fails. Options: `--sizes`, `--themes`, `--fit` (pages that must not scroll down), `--action` (a primary action), `--exempt`, `--wait` (a condition that says the page is drawn; the default is any text in `main`, which a lazy dev route meets too early) and `--problems` (failures only). It loads `e2e/layoutAudit.ts` as it is, so it needs Node 22.18 or newer.
- A theme in a screenshot: the headless browser follows its system, so store the choice and reload once, which also runs the head script: `--wait "(sessionStorage.getItem('s') ? <ready> : (sessionStorage.setItem('s', '1'), localStorage.setItem('theme', 'dark'), location.reload(), false))"`.

### End-to-end

`pnpm e2e` (`playwright.config.ts`) starts `cargo run -p mtg-server` (an empty `DATABASE_URL` gives the in-memory store and the built-in demo decks; `MTG_DWELL_MS=0` passes for idle seats at once, since the default wait would take the full game from about 8 s to between 29 and 35 s) on port 8301 and `pnpm build` plus `vite preview` on port 5301, both new for every run.

- `E2E_SERVER_PORT` and `E2E_WEB_PORT` override the ports (defaults 8301 and 5301, `e2e/ports.ts`) to run several suites at once; the Vite dev server that serves `/dev/table` to `fit.spec.ts` listens on `E2E_DEV_WEB_PORT` (the web port plus 1000). `E2E_REUSE=1` keeps servers already listening there; `E2E_TRAIL=1` prints every answered decision; `--repeat-each=N` repeats the game.
- `e2e/seeds.ts` gives each server an engine seed (`MTG_SEED`, [Configuration](server.md#configuration)): every game on it shuffles alike, so a failing game replays exactly; the servers log the seed of every game (`game created`) and a failed Commander or precon run attaches `seed.txt`. ## Conventions

- Cards the engine plays only in part (Partial, Manual or Stale) are "played by hand" everywhere: the lobby seat, the choosers, the builder, the precon browser and the card at the table take the words from `lib/byHand.ts` (`BY_HAND`, `BY_HAND_TITLE`, `PARTLY_BY_HAND`, `cardsByHand`, `byHandCopies`), the deck state `manual_play` reads "Played by hand", and a card's mark keeps the name of its support state (Verified, Partial, Manual, Stale, Unplayable). `lib/byHand.test.ts` fails on any other spelling in the sources and the e2e specs, and on the phrase written outside the module.
- The words a player reads spell "color" the American way, as the rules, the cards and the server's deck issues do (`spelling.test.ts` scans the strings and the JSX text of `src`); identifiers and the wire key `colour_identity` of the house rules keep theirs.
- Server-held state is shown, never predicted: ready, yields, stops and Full Control change on screen only when the server says so.
- Colour never carries meaning alone, and live regions are polite. A row of cards, a ladder row or a list is one tab stop (arrows, Home, End); a control that must keep focus when it cannot act is `aria-disabled`, not `disabled`.
