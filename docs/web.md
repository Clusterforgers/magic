# Web client

The browser client of the Magic platform: the net and play layers in `web/src/net` and `web/src/play`, and the pages in `web/src/features`. Wire contract: [protocol.md](protocol.md); transport: [server.md](server.md).

## Stack and layout

React, Vite, Tailwind, shadcn/ui on Base UI, TanStack Router and zustand. Commands are in `CLAUDE.md`.

- Pages live in `src/features` (`auth`, `create`, `game`, `games`, `table`); `src/routes` only picks them. The Vite plugin rewrites `routeTree.gen.ts` on `pnpm dev` and `pnpm build`; commit it with the route change.
- `src/net` (REST, socket) and `src/play` (session, store) hold the client. `src/components/ui` is shadcn (`pnpm exec shadcn add <name>`). `src/protocol` has the ts-rs bindings and the transcripts Rust writes.
- The dev and preview servers proxy `/api` and `/ws` to `MTG_SERVER_URL` (default `http://127.0.0.1:8080`) and keep the browser's `Host`, which the server's Origin check compares with the page's `Origin`.

## Data flow

- `net/api.ts` checks REST bodies at runtime; a failure is an `ApiError` with a code of `crates/mtg-server/src/api.rs` or a local one. `net/parse.ts`: `parseFrame` is the only door from the wire (JSON, known `type`, required fields, 1 MiB cap); garbage is a `FrameError`, never a throw.
- `net/socket.ts`: `GameSocket` sends `Join` first and once per connection. `net/pacer.ts` holds sends to a burst of 30, then 15 a second; the server allows 40 and 20 and closes a socket over it with 1008.
- `play/view.ts`: pure ports of `StateView::apply`; unchanged objects, players and zones keep their identity.
- `play/session.ts`: `createSession({game, token, name})` owns the socket, applies the client rule of [protocol.md](protocol.md) and writes the zustand store (`play/store.ts`) that screens read with `useStore(session.store, selector)`.

The session's rules:

- A Snapshot sets the base and `seq`. A batch whose `from_seq` is not `seq` (or any batch but the one at 0 while there is no view) sends one Resync; nothing is applied and decisions are ignored until the next Snapshot.
- A `Decision` replaces `pending`. `answer()` sends once per decision id; a Snapshot or a lost connection forgets answered ids, so the server's repeat can be answered.
- `GameOver` sets `result` and makes a later close final. `StaleDecision` and `IllegalAnswer` give a notice and a Resync; `BadMessage` and `Internal` only a notice.
- A wrong token is a refused upgrade, which a browser reports as 1006, so the client retries forever (`attempt` counts).

| Close or message | Socket status |
|---|---|
| 1001, 1006, 1013 and any code not listed below | `reconnecting`: retry after 250 ms doubling to 15 s, less up to 50 % jitter; a Welcome resets it |
| 4000 | `replaced`, no retry; `connect()` takes the seat back |
| 1000, 1002, 1007, 1008, 1009; `Error` UnsupportedVersion or UnknownGame | `stopped`, reason in `notice` |
| any close after `GameOver` | `stopped`, no notice |

## Create and game pages

- `/` (`create/CreateGamePage`): decks from `api.listDecks()`, 2 to 12 seats with a name and a deck, format Normal (Commander shown disabled). `create/form.ts` repeats the server's checks; `create/apiErrors.ts` words every `ApiError` code.
- `/game/$gameId#seat=<n>&token=<token>` (`game/GameRoute`) reads the fragment from the router's raw `location.href`, because its `hash` is percent-decoded.
- A seat token lives only in the fragment, which a browser never sends. `components/SeatLinkRow` prints it only inside a `data-share-link` anchor, and tests scan the page for tokens outside those (`test-utils/leaks.ts`). `lib/invites.ts` keeps the host's links in `sessionStorage` (every access in try/catch) so the lobby can hand them out after the create page is gone.
- `game/GamePage` makes one session per (game, seat, token) and connects one microtask after mount, so StrictMode's mount, unmount, mount opens one socket. `game/gameContext` gives `useGame()` (`game`, `session`, `lookup`) and `usePlay(selector)`; `lookup` is `GET /api/games/{id}`, polled every 3 s in the lobby.

| Store | Screen (`connectionOf`, `game/connection.ts`) |
|---|---|
| no seat link and not signed in | `SeatLinkMissing`; no socket |
| `phase` over | `GameOver`; no connection notice |
| `status` replaced or stopped | `ConnectionNotice` alone: the reason and a button to connect again |
| idle or connecting, never welcomed | "Connecting to the game…" |
| `reconnecting`, `attempt` below 5 | "Connection lost. Reconnecting… (attempt N)" |
| `reconnecting`, `attempt` 5 or more | "Cannot reach the game" and "Try again now"; the socket keeps retrying and a Welcome moves the page on |
| welcomed | `Lobby` while `phase` is lobby, `GameTable` while playing |

After a Welcome the lobby or table stays under the reconnect notice. A `notice` shows above any other screen as a dismissible alert, unless a connection notice already prints it.

## Lobby

- The `Lobby` message ([protocol.md](protocol.md)) is kept whole as `lobby` (`{seats, needed}`) and dropped when the connection goes or the game starts, so it is only what the open socket last heard.
- `game/lobbyModel.ts` (pure) makes the rows. The roster wins; before it and while reconnecting the REST lookup stands in, with "Seat N" for an unnamed seat. This page's own seat is connected exactly when its socket is open.
- A polite live region (`aria-live`, no role, because the connection banner is the page's `status`) announces what changed between two looks (`announcement`): at most three changes, none for this seat's own connection or for the step from stand-in rows to real data.
- The button follows the server's roster ("Ready", then "Not ready"). A reconnect sends no Ready of its own, and the second click of a double click is ignored (`event.detail`), so a fast connection cannot take the Ready back by accident.

## The table

The table is `features/table/GameTable.tsx`, rendered with no props while `phase` is `playing` (see Table below). `GamePage` puts notices and the reconnect banner in a narrow column above it, so the table uses the full width.

`features/table/` is the table; decision prompts live in `prompt/` (next section). `GameTable` takes no props: it reads with `usePlay(selector)`, chats through `useGame().session.chat`, and starts from `TableOptionsContext` (`mode`, `focus`; only the dev route sets it).

- Layout, `layout.ts` (pure; tested for 2 to 12 seats and every viewer): `arrangeSeats` lists the opponents in turn order after the viewer, who is drawn last, at the bottom. Grid mode (default up to 4 seats): every opponent's panel and battlefield in `min(3, opponents)` columns (fewer on narrow screens). Focus mode (default from 5): a tile per opponent and one opponent large; the default focus is the active player, else the priority holder, else the next seat still in, and follows the turn until a tile is chosen (click, Enter or Space; "Follow the turn" undoes it). The toolbar switches either mode in any game. From 8 seats cards are compact; lands always are.
- Parts: `SeatPanel` (name, life, mana pool, mulligan line, eliminated reason, library and hand counts, hand strip or card backs, graveyard top card and list dialog, exile of that owner, command zone, a commander damage and tax slot that says "not tracked yet"), `Battlefield` (rows of lands, other permanents, creatures, creatures toward the middle), `Card` and `CardFace` (a text face; a `data-slot="card-art"` box waits for an image id in `ObjectView`; tapped is a quarter turn plus the word "Tapped", and sick, damage, attacking, blocked and blocking are words too), `CentreStrip` (turn banner, priority, during the opening hands `OpeningStatus`, the decision line: the prompt of this seat's decision, else a read-only "Waiting for ...", and the "nothing to do" note), `StackPanel` (top first, with controller), `Drawer` (log sentences from `eventText.ts`, chat; a side column from 1024 px, bottom tabs below), `CardPreview` (hover or focus shows the large card with its abilities, docked away from it; a click pins it, Escape or Close dismisses).
- Rendering by construction: a `Card` reads only its own object and combat role and is `memo`; a row reads its ids through `useShallow(battlefieldRow)`, and `selectors.ts` splits the shared battlefield by controller once per view. A batch that taps one permanent redraws that card and no row; `perf.test.tsx` counts the renders at 12 seats with 40 permanents each, and fails without `memo` or `useShallow`. Each row of cards is one tab stop (roving focus: arrows, Home, End).
- Seams for the prompts: `Card` takes optional `highlight` (`legal | dimmed | selected`) and `onSelect(id)`, which override what the active prompt gives it (see Prompts); cards carry `data-object-id` and seat panels `data-seat`; `[data-slot="decision-line"]` in `CentreStrip` is where the prompt goes. Not in the views yet, so not drawn: card art, counters, attachments, commander damage and tax.
- Opening hands: while `view.stage` is `Mulligan`, `OpeningStatus` (a region "Opening hand decisions" in the centre strip, `OpeningStatus.test.tsx`) lists every seat in seat order with what it is doing, from what the table view already says publicly (`PlayerView.mulligan` and `mulligans`, no engine or protocol change): "You: deciding", "Bo: keeping", "Cy: taking a mulligan · 1 mulligan taken", "Eli: keeping, bottoming 2 · 2 mulligans taken" (`describeOpening` in `turnText.ts`; "getting a new hand" for a seat whose mulligan is being dealt). It is there for any table size and layout, so at five seats and more, where only one opponent has a panel, every seat's progress is still on the screen; the panels keep their longer "Mulligan: ..." line. Dev: `?prompt=mulligan|mulligan-free|bottom` now put the dev table in the mulligan stage with the other seats spread over the steps.
- Concede: `ConcedeButton` sits right of the layout toolbar (one more Tab stop before the opponent tiles) and opens a `components/ui/alert-dialog` ("Concede the game?", Keep playing focused first, Escape cancels). Confirm calls `session.concede()` once and closes; a refused send (socket not open) keeps the question up with an alert. `canConcede` (selectors) hides the button for a client without a seat, a seat that is out, and a game that is over. The loss comes back as `PlayerLost { reason: Conceded }`: the seat panel already says "Eliminated: conceded" (`data-eliminated`) and the log "Bo conceded", so no extra marking exists.
- Your turn: while the viewer is the active seat of a running game (`isYourTurn` in `selectors.ts`: stage Turns, no result), the turn banner (`CentreStrip`) and the viewer's own `SeatPanel` take the `your-turn-cue` utility from `index.css` (a 2 px ring and an amber glow, `data-your-turn` for tests) instead of their ring classes, and the banner shows a "Your turn" badge so the cue does not rest on colour. The glow pulses only inside `@media (prefers-reduced-motion: no-preference)`; otherwise it stands still (`yourTurnCss.test.ts` guards that no animation leaves the media query). The tab title is `features/game/useTurnTitle`, which `GamePage` feeds into `usePageTitle` (so the old title comes back on unmount and the order of effects does not matter): "Your turn · Game · Magic" during the viewer's turn, and "● Your move · Magic" while the tab is hidden (`hooks/useTabHidden`) and the viewer holds a decision, alternating with the other title every second, or held still under reduced motion (`hooks/useReducedMotion`, which reads `matchMedia` and follows changes). Only the table screen is decorated, not the lobby, connection notices or result.

## Prompts

`features/table/prompt/` answers the decision this seat faces. Part 2a is the framework, the Priority prompt (`kinds/Priority.tsx`) and the "nothing to do" note; the other kinds are placeholders until their part.

- Host: `PromptHost` (in `CentreStrip`, in place of the read-only line while `pending.decision.player` is this seat; `ownDecision` is the selector) renders `PROMPTS[kind]` with that kind's `options` inside one scope keyed by decision id. A new id remounts the prompt with an empty selection; a decision of another seat keeps the "Waiting for ..." line.
- Registry: `registry.ts`, one line per decision kind. A kind not built points at `kinds/<Kind>.tsx`, which exports `<Kind>Prompt = UnsupportedPrompt` ("This decision is not supported in the UI yet", no controls). To build a kind, replace the body of its file and keep the export (`PromptComponent<'Kind'>`, props `{ options }`); `registry.ts` needs no edit.
- `usePrompt()` gives `{ id, name, decision, answer, selection }`. `answer(a)` wraps `session.answer`: once per decision, `false` when already sent, refused by the socket (a retry is allowed) or when the store holds another decision by now. `selection` is `{ ids, has, toggle, set, clear }`, in order of choice, empty for every new decision id.
- `PromptLayout` (prop `text`, the controls are its children) draws the shared shape: "Your decision: X", one polite live sentence, a row of controls (use `Button` with `className="h-10 px-4"`). `ManaChoice` (which mana a permanent with several mana abilities makes; focus moves in, Escape cancels) is reusable.
- Card marks, `prompt/marks.ts`: a prompt calls `useCardMarks(marks, onSelect, { toggles })` with a `Map<ObjectId, 'legal' | 'dimmed' | 'selected'>`; `markCards(own, legal, selected)` builds one (own cards dimmed, legal and selected on top) and `useOwnCardIds()` lists the viewer's hand and battlefield. `onSelect(id)` runs on a click or Enter/Space on a legal or selected card; a dimmed one only previews. `toggles: true` is for selections (the card reads as pressed), the default for a click that acts at once. `GameTable` provides the store; each `Card` subscribes to its own id only, so publishing redraws just the cards whose mark changed (`perf.test.tsx` counts it). A card's own `highlight` and `onSelect` props still win. Marks go when the prompt unmounts.
- Priority: lands in `playable_lands`, spells in `castable` and permanents with `mana_abilities` are legal, the rest of the viewer's hand and battlefield dimmed; a click answers `PlayLand`, `CastSpell` or `ActivateMana`; a permanent with several mana abilities selects itself and shows `ManaChoice`. The sentence says what may be done and, over a non-empty stack, that you are responding to its top spell. Passing is `prompt/PassControls` (below); the words of the buttons are `prompt/passWords.ts`, which is display only.
- Nothing to do: the newest `NothingToDo` event for the viewer (not an earlier turn) shows "You have no creatures that can attack|block" under the strip until the viewer has been asked something and answered it, since the engine usually asks for priority right after.

- Mulligan, BottomCards, Discard: Mulligan marks no card and leaves the hand strip as it is; its sentence (`mulliganText.ts`) says the hand size, the mulligans taken (and how many were free), what keeping puts on the bottom and what another mulligan does (a free one "adds no card to the bottom"), all read from `bottom_if_keep`, `bottom_if_mulligan` and `free_mulligans` of the options, "Keep" and "Mulligan" answer `MulliganChoice` (Mulligan is disabled when `can_mulligan` is false), and a line under the buttons names the other seats whose `mulligan` is `Deciding` or `Bottoming`. BottomCards and Discard are one component, `CountedChoice` (`countedText.ts` has the words): the offered cards are legal toggles and the rest of the viewer's cards dimmed, the sentence counts "2 of 3 chosen" and says what is left, a card past the count is refused with a hint in the same live sentence (nothing is dropped), Confirm waits for exactly N (N is cut to the offered cards) and answers in the order chosen. Dev: `?prompt=mulligan|mulligan-free|bottom|discard`.

- PayMana: the summary (`PaymentSummary`) shows the cost as mana symbols, the floating mana (one button per kind, "left" counted), the payment so far (one chip per piece, a chip takes its piece back, Undo, Clear) and what is still owed; one live sentence (`payText.ts`) says the last change and what to do. Untapped permanents with a mana ability are legal, the rest of the viewer's cards dimmed; a click adds the source (toggle: clicking a chosen one takes it back), and a permanent that makes several kinds of mana asks which with `ManaChoice` (only kinds that still fit, two abilities of one kind count as one). Mana that would be wasted is not offered (`payment.ts` `fits`), so the payment is complete exactly when the engine's check passes; a permanent is tapped once. The check is the engine's: `payment.ts` resolves the cost the way `ManaCost::resolutions` does (each hybrid and Phyrexian symbol paid in one of its ways, `resolutions`), puts the mana against the units that leaves (each kind meets its own, the rest goes to generic) and calls a payment valid when some resolution leaves nothing owed and no mana over; `payment.test.ts` holds it to an independent symbol-by-symbol check for many costs and every choice of life. "Confirm payment" (disabled until then) sends `PayMana: { Manual: { pool, taps, life } }`, "Pay automatically" (only when `auto_available` and nothing, life included, is chosen yet) sends `Auto`, and once something is chosen and the cost is not yet covered it gives way to "Pay the rest for me" (same condition), which sends `PayMana: { Complete: { pool, taps, life } }` with the picks so the engine pays what is owed (and, as for Auto, life only where no mana can); "Cancel casting" (only when `can_cancel`) sends `Cancel`, and the live sentence stops mentioning cancelling without the flag and offers "pay the rest for me" while `auto_available`. Dev: `?prompt=pay|pay-short|pay-locked` (`pay-locked` has `can_cancel` false).
- Hybrid and Phyrexian symbols (`manaSymbols.ts`, `cardModel.ts`, `ManaPips.tsx`): `manaSymbols.ts` ports what the client needs of `ManaSymbol` (printed text, mana value, the ways to pay, whether life can pay). `costPips` gives each symbol a pip: a hybrid symbol is a disc split on the diagonal with a letter in each half (`bg-linear-to-br` with a hard stop, `PIP_FROM`/`PIP_TO` in `cardSize.ts`), `{2/W}` has its 2 on the grey half over the colour, a Phyrexian symbol is its colour with the phi mark (`ϕ`), a hybrid Phyrexian one is split with the phi in a pill, `{C/W}` splits colourless and the colour. Each pip carries its printed form in `data-pip` and a spoken name (`white or blue mana`, `white mana or 2 life`, `green or blue mana or 2 life`, `white mana or 2 generic mana`, `colorless or white mana`, `colorless mana or 2 life`); the group names the whole cost (`Mana cost: 2 generic, white mana or 2 life`). `costText` writes `{2}{W/P}{G/U/P}` as a card does and `costWords` (`payText.ts`) says it in a sentence (`1 white or 2 life and 1 green or blue or 2 life`).
- Paying life (PayMana): a cost with a Phyrexian symbol gets a Life row in `PaymentSummary` with the life total and one switch per symbol that life can pay (`Pay 2 life instead of white mana`, numbered when symbols are equal: `, 1 of 2`; `aria-pressed`, `aria-disabled` when it cannot be flipped, never `disabled`). A switch works while the life paid stays within `max_life` and the mana already chosen still has a place (`payment.ts` `lifeChoices`); taking life back always works. The payment keeps the symbols life pays (`life` in `PayMana.tsx`, a list of places in the cost) and sends `life: 2 × that`; `owed` leaves them out and still shows a hybrid symbol as hybrid until mana meets it. The sentence names the last change, says `The cost is covered, paying 2 life (18 left)`, and offers `pay 2 life for a Phyrexian symbol` beside the lands; "Clear" takes the life back too. When `auto_available` is false because only a payment that takes the last life would do, the prompt still lets the player pay it by hand. Dev: `?prompt=pay-hybrid` (`{1}{G/W}{2/U}{W/P}{G/U/P}` with 20 life, the spell in the hand carries the cost too) and `pay-low-life` (the same with 3 life: one symbol can be paid, not both). A plain cost shows no life row and no mention of life.

- DeclareAttackers, DeclareBlockers: both mark cards as toggles and write a note on the cards they pair (`useCardNotes` in `marks.ts`: a `{ label, words }` per card id, drawn as `data-slot="card-note"` on the face and spoken after the mark; a note never makes a card clickable; flipping the toggle flag now redraws only the marked cards, which keeps a 12-seat table cheap; `combatPerf.test.tsx` counts it). Attackers: the offered creatures (those with a defender) are legal, the viewer's other cards dimmed; click, Enter or Space puts a creature in the attack or out of it and its card says "At <seat or planeswalker>". With one possible defender there is nothing to choose; with several an "Attack at" select sets where creatures chosen next go, "All at <aim>" re-aims everything chosen, "Attack with all" adds every offered creature, and a list under the buttons has a select per attacker. The sentence sums up ("3 attackers: 2 at Cy, 1 at Bo"); "Confirm attack" (needs one) answers `[creature, target]` in the order chosen, "No attack" answers an empty attack, "Clear" empties it. Blockers: legal blockers are those with something to block; choosing one (click, Enter, Space; again to cancel) marks it chosen, the attackers it may block legal and every other attacker in the combat dimmed, and opens a list of buttons, one per attacker with power, toughness and controller, so an attacker on a seat that is not drawn can be picked; focus moves to the first button, Escape or Cancel closes it and focus returns to the blocker's card. Picking pairs them ("Blocks <attacker>" on the blocker, "Blocked by <blocker>" or "Blocked by 2" on the attacker); a paired blocker can be chosen again to move or take back its block (also "Change" and "Remove" in the list of blocks). A blocker blocks one attacker, as the engine demands; "Confirm blocks" answers `[blocker, attacker]` pairs in the order made, "No blocks" an empty list. Who may be blocked comes only from `can_block`, so attackers aimed at other seats are never offered. Same-name creatures get a number in lists ("Goblin 1"). Dev: `?prompt=attack|block` also change the fixture's moment (`DEV_TABLES` in `dev/prompts.ts`): the viewer's own declare-attackers step with a planeswalker to attack, or six attackers (four at the viewer) to block.

- AssignDamage: the options are `{ attacker, power, blockers }` and the answer `[blocker, amount]` pairs; the engine takes any whole-number split that adds up to `power` (no lethal-first order since the Foundations rules, no trample or player target yet), so that is all the prompt enforces. One row per blocker: name, "Toughness 4, 1 damage marked, lethal: 3", minus, number box, plus and "Lethal" or "2 short of lethal". The first split is the default of `prompt/damageSplit.ts` (lethal damage in the offered order, the rest to the last; it follows the creatures until the first edit), edits are clamped so the total never passes the power, and a button at its limit is `aria-disabled` so keyboard focus is not lost. Confirm (the form's submit, so Enter in a number box sends) is disabled until the total equals the power, and a `role="status"` line says why. Only blockers that get damage are in the answer. Blockers are marked `legal` (nothing dimmed) and the row with focus `selected`; a click or Enter on a blocker's card focuses its row. Gaps: views carry no keywords, so deathtouch is not in the lethal hint, and commander damage and tax are still not in `PlayerView`/`ObjectView` (the seat slot stays "not tracked yet"). Dev: `?prompt=damage` (two blockers), `damage3`, `damage1`.

## Combat overlay and previews

`features/table/combat/` draws what combat will do from the `combat_forecast` the engine puts in the table view (`engine.md`, `protocol.md`; `net/parse.ts` checks it down to its leaves). The client never works an outcome out: it shows the engine's numbers and hides them when they cannot hold.

- The seam: `useBlockPreview()` (`forecast.ts`) is the forecast to draw, and everything that draws one asks it: the overlay's colours, the marks on cards and seats, the key, the sentences and the outcome of the DeclareBlockers and DeclareAttackers prompts. It is the table's forecast while no choice is pending, and the engine's preview of the choice being made otherwise (`previewFor`, see Block preview below): the table's forecast describes combat as it stands, which has none of a pending block or attack. `prompt/blockPreviewSeam.test.tsx` swaps the seam to show that nothing else needs to change. `CombatProviders` (one wrapper in `GameTable`) publishes the forecast to `drawn.ts`, a store that gives each card and seat panel only its own entry (the pattern of `prompt/marks.ts`), so a forecast arriving or a block chosen redraws just the creatures it mentions (`combat/combatMarksPerf.test.tsx`, 12 seats).
- Lines: `CombatOverlay` is an SVG over the table column (`aria-hidden`, `pointer-events: none`, mounted only while a line exists) in two layers, the lines under the centre strip and a faint copy above it, so a line that passes behind the prompt can still be followed. `plan.ts` (pure) turns the combat view, the forecast and the unsent choices into lines: attacker to seat or planeswalker (muted, thin), blocker to attacker (strong, coloured by the pair's outcome in the forecast: attacker dies, blocker dies, both die, both survive; a double block gives each blocker its own), unsent choices dashed. `geometry.ts` (pure, boxes in, path out; table-tested) joins two boxes edge to edge with a bowed curve and an arrowhead. `rects.ts` finds the boxes in the DOM relative to the overlay (a card is `button[data-object-id]`, measured by its `card-face` so a turned card is the card as seen; a seat is its `[data-seat]` panel whole, else its `[data-tile-seat]` tile; a card that is not drawn stands in as its controller's panel or tile, and lines that would coincide are drawn once). It measures when the anchors appear and again, once per frame (`createScheduler`), when a ResizeObserver, a MutationObserver (cards entering or leaving, `data-tapped`, `data-size`), a scroll anywhere in the table, `transitionend`, a window resize or fonts say something may have moved, never per render. Tests inject a `RectProvider` with fake frames (`test-utils/rects.ts`; jsdom has no layout) and `domContract.test.tsx` runs the real one over stubbed boxes. Lines draw themselves in over 280 ms (`combat.css`, only inside `prefers-reduced-motion: no-preference`, guarded by `combatCss.test.ts`); colours are tokens with a light and a dark value.
- Marks: a creature the forecast says would die has `data-doomed`, a grey cracked overlay and a skull badge with "Dies"; every creature that would take damage has a "-N" badge (`ForecastMarks`, drawn over the card as seen, so a tapped attacker's badge is upright). A seat the forecast attacks shows "life → life after" and a "Lethal" mark on its panel (`LifeForecast`), or "No combat damage". All of it is decoration with the words elsewhere: the card's spoken name ends ", would take 3 damage and die", the panel has the sentence "Life would go from 5 to -1, which is lethal", the card preview says "Combat forecast: would die", and a visually hidden list "Combat forecast" in the centre strip has one sentence per attacked seat (first) and per attacker ("Bo's Hill Giant is blocked by your Grizzly Bears: Bo's Hill Giant would survive, your Grizzly Bears would die."). The key under the turn banner (`CombatLegend`) lists only the kinds of line on screen.
- Prompts: DeclareBlockers publishes its pairs (`usePublishPending`, `pending.ts`) and lists them as "Your Grizzly Bears blocks Bo's Hill Giant" with Change and Remove; its outcome part is the seam's forecast ("If you do not block", then the sentences; "If you block like this" with the engine's preview once a block is pending), "Checking outcome…" while that is asked, or "Outcome shown after you confirm." when no preview comes, and a block chosen or changed takes the marks away until the engine has answered for it. DeclareAttackers publishes the attack so far, which is drawn as dashed muted lines to the seat or planeswalker each creature goes at, and shows the same outcome part ("If you attack like this").
- Dev: `/dev/table?prompt=forecast` (the viewer holds priority after five attackers were blocked: a double block, three single blocks that show all four outcomes, one unblocked attacker that is lethal; `&turn=you` flips the sides) and `?prompt=block` (the viewer faces lethal damage, with the forecast "if you do not block" and, with a third seat, another defender's double block). `dev/devForecast.ts` works the forecast out from the fixture's cards, for the dev table only.
- Gaps: the forecast lists creatures and players, so an attacked planeswalker gets its line but no damage mark; no animation but the line drawing in (the effects slice is separate).

While a player is still choosing blockers or attackers the engine says what the choice would do (`ClientMessage::Preview` and `ServerMessage::Forecast`, `protocol.md`; `Engine::preview_forecast`, `engine.md`). The client still works out nothing: it asks, waits and draws the reply.

- Session: `session.preview(decision, answer)` sends one `Preview` for the pending decision and remembers the key of the answer (`play/preview.ts` `previewKey`: the answer as JSON, so the order of choice counts). It is false when that decision is not the pending one, when the socket is not open and once an older server has refused one. The server answers every preview, in order, so a reply is matched to its question by order and only the reply to the newest question is kept, as `store.preview = { decision, key, forecast } | null` (`forecast` null: the engine had none for that answer). The store drops it when the decision is answered or replaced, with a snapshot, at game over and with the connection; a reply whose decision is no longer pending is ignored. An `Error{BadMessage}` that arrives while a preview is unanswered is taken for an older server refusing a message it does not know: no notice, and no more previews until the next connection.
- The seam: while no choice is pending, `useBlockPreview()` is the table's `combat_forecast`. While one is (`pendingAnswer` of what the prompt published) it is the stored preview if that is for the pending decision and has the same key as the choice, else nothing (`previewFor`, a pure table-tested rule). A forecast is therefore never drawn for a choice it does not describe: the marks go the moment the choice changes and come back with the reply. Cards, overlay colours, life-after and lethal marks, the key and the sentences needed no change.
- Asking: `usePreviewRequest(decision, answer)` (`combat/usePreviewRequest.ts`) is used by both prompts with the answer that Confirm would send (`blocksAnswer`, `attacksAnswer`: the same functions the seam uses, so the key of the question is the key of the choice). It asks `DEBOUNCE_MS` (80 ms) after the choice last changed, so a run of clicks asks once with the latest choice, and its cleanup cancels a question that the choice, the decision or the prompt has outgrown. It returns `idle | checking | ready | unavailable`: checking from the change of choice until the reply, ready when the store holds a forecast for it, unavailable when the reply holds none, when the session would not send and `GIVE_UP_MS` (1.5 s) after sending without a reply (a late reply is still taken).
- Words: `prompt/PreviewOutcome.tsx` is the section under the controls of both prompts (`data-slot` `block-outcome` or `attack-outcome`, `data-state` `checking | ready | unavailable`): a heading and the engine's sentences, or "Checking outcome…", or "Outcome shown after you confirm.". While checking, the last list of sentences stays in the page, `aria-hidden` and `invisible`, so the section keeps its height instead of jumping with every click. One polite live region (`data-slot="outcome-live"`, screen-reader only, except that it is the node showing the fallback words) says one sentence per change: `forecastSummary`, such as "If you block like this: Your Grizzly Bears would die. You would take 3 damage."; nothing is said while checking. The sentences under "Combat forecast" for screen readers (`CombatLegend`) follow the seam too.
- Attackers: once an attacker is chosen the prompt shows the section ("If you attack like this") and the attacked seats show "life → life after" and the lethal mark while the attack is still being chosen. Nothing is asked for an empty attack.
- Dev: `fixtureSession(store, { previewAfter })` answers previews with `dev/devForecast.ts` `devPreview`, the dev table's own stand-in for the engine, after that many milliseconds. The dev route does so after 120 ms, or after `?preview=<ms>` (0 to 10 000), which is also how "Checking outcome…" is looked at: `/dev/table?seats=3&prompt=block&preview=1200`. Test tables leave previews off, so with one a choice falls back to "Outcome shown after you confirm." a moment later (the prompt tests wait for it).
- Tests: `play/preview.test.ts` (the session, and a replay of the exchanges in `protocol/fixtures/block-preview.json`, which Rust generates from the engine), `net/parsePreview.test.ts`, `prompt/PreviewLive.test.tsx` (the whole flow over a fake socket with fake timers: debounce, outdated replies, checking, fallbacks, forgetting with the decision, attackers), `combat/forecast.test.tsx` (the seam), `combat/forecastText.test.ts` (the summary), `dev/devPreview.test.tsx`.

## Table feedback

`features/table/fx/` draws short animations over the table for what a batch did: attack, block, damage, death, life and entry. They are decoration on top of the true state, which the table already shows when they start: nothing waits for them, no answer is delayed, and ending one only removes an attribute.

- Pipeline: `useTableFx` (in `GameTable`) calls `batch.ts` `watchBatches(store, fx)`, a subscription to the play store. `batchBetween(prev, next)` takes a change for a batch when `seq` moved on by exactly the events appended to the log from where `prev` stood; a snapshot (the first, a resync, a reconnect, an older one), a decision, chat or a status change never counts, so only live play animates. `derive.ts` `deriveEffects(before, after, events)` is pure and returns `Effect[]` in a fixed order (life by seat, then `attacked`, `blocked`, `damaged`, `entered`, `died`, each by object id). The batch's object diff is not passed on: it is read off the two moments, since the fold keeps the identity of every unchanged object.
- Where each effect comes from: `attacked` and `blocked` from `AttackersDeclared` and `BlockersDeclared` plus the combat diff (a whole combat can run in one batch when nobody had a decision, and leave no attackers behind); `damaged` on a permanent from `DamageDealt` (summed), else damage newly marked, while it is still on the battlefield; `damaged` and `healed` on a seat from the life total diff (no event says life); `entered` for a permanent that was not on the battlefield; `died` for one that went from the battlefield to a graveyard or that `CreatureDied` names (a token), at most 24 a batch, carrying its last look (`snapshot`), its row and the card that stood after it. A player who loses takes their permanents out of the game, so they vanish without ghosts. A creature that dies in the batch that declared it an attacker or blocker gets its ghost only, and the damage that killed it floats on the ghost.
- Store: `store.ts` `createFx(options)`. `play(effects)` keys them by card, seat and battlefield row (`FxState` is replaced, never changed, so a card whose entries did not change keeps its snapshot); one timer per kind and batch removes them after `FX_MS` (entered 350, attacked, blocked and died 500, damaged and healed 550 ms); a repeat on the same target replaces the running one; at most 120 effects a batch. `mode` (`off | reduced | full`) is read at every batch: `reduced` while the system asks for less motion (`prefersReducedMotion` in `hooks/useReducedMotion`) plays only the still highlights, no ghost and no entrance. `clear()` ends everything and cancels the timers, which the table does when it goes. Timers are injectable (`FakeTimers`).
- Switch: `TableOptions.effects`; left out it is `EFFECTS_BY_DEFAULT`, on everywhere except under vitest (`import.meta.env.MODE === 'test'`), so every other test sees the table with no timers and no extra markup. A test turns it on with `renderTable({ options: { effects: true } })` and `vi.useFakeTimers()`. `effectsSlow` multiplies every duration.
- Drawing: `Card` (`useCardFx`) sets `data-fx="<kinds>"` and `data-fx-side="own|other"` on its button and floats the damage; `LifeFx` wraps the life figure in `SeatPanel` and `SeatTile` (`data-slot="life"`, `data-fx`, a float of "-N" or "+N"); the battlefield rows hand `useGhosts(seat, row)` to `CardRow`, which puts each `GhostCard` back in front of the card it stood before (`withGhosts`) as an `aria-hidden` `li` with no `data-object-id` and nothing focusable. Looks: an attacker or blocker leans 0.9 rem (up from the viewer's side, down from the others') and glows (amber for an attack, blue for a block); damage flashes the face red, shakes it and floats "-N"; a ghost cracks, greys and fades while it closes the gap it leaves; a life total pops, flashes red or green and floats the amount; an entering permanent pops in. React redraws only the card, life figure or row whose entries changed, at the start and at the end (`fxPerf.test.tsx` counts it at 12 seats).
- Stylesheet: `fx/fx.css`, imported by `index.css`. Every animation is inside `@media (prefers-reduced-motion: no-preference)`; under `reduce` an effect is a still outline for as long as it would run. The durations are the custom properties `--fx-<kind>-ms`, which `fxCss.test.ts` holds equal to `FX_MS` (it also checks that no motion leaves the media query and that every rule needs an effect attribute); `--fx-slow` stretches them.
- Accessibility: floats, ghosts and cracks are `aria-hidden` and add no tab stop; labels, the log and the life totals say the true state from the first moment (`TableFx.test.tsx` compares what a screen reader reads with the layer on and off).
- Looking at it: `/dev/table?fx=attack|block|damage|death|life|enter` plays that move once, 600 ms after the page loads (and turns the layer on even under vitest); the buttons at the top of the page play any move again; `slow=2..20` stretches every effect. `dev/fxScenarios.ts` builds each move as a real batch and `applyBatchToStore` folds it as the session does, so it takes the same path as a game. To look at one frame, freeze it: `node scripts/ui-shot.mjs "http://localhost:5314/dev/table?seats=2&fx=death&slow=10" out --widths 1400 --wait "(() => { const a = document.getAnimations(); if (a.length === 0) return false; a.forEach((x) => { x.pause(); x.currentTime = 2000 }); return true })()"` (use localhost, not 127.0.0.1).
- Not done: no effect for a permanent that goes to a hand, exile or library, none for a spell on the stack, no stagger between the effects of one batch, no sound, and no lines between attackers and blockers (Combat readability).

## Pace controls

- Passing (`prompt/PassControls.tsx`, `passWords.ts`, `usePrimaryKey.ts`; the player's words were "I'm not the biggest fan of pass priority"): the primary button (`data-slot="primary-action"`, answers `Pass`, disabled when `can_pass` is false) says what passing does now, from the step, whose turn it is and the top of the stack (`primaryLabel`, a pure function tested over every step and both turn owners): "Resolve <name of the top spell>" over a stack, on the viewer's turn "Next: <the next step>" ("Next: Combat", "Next: Declare attackers"... and "End turn" in the End step), on anybody else's turn "Continue". The phrase "pass priority" is never a visible label; it is the `aria-description` ("Passes priority; if nobody responds, Lightning Bolt resolves."). The keys are shown as caps on the buttons (hidden on narrow screens, where there is no keyboard), as tooltips, as `aria-keyshortcuts` and as a legend in the "More ways to pass" menu. At 390 px the primary button takes a row of its own and "End turn" and the menu sit under it.
- The yield line (`YieldIndicator`, in the centre strip beside whatever decision there is): while the store's `yielding` is set (the server's word: every `Welcome` and `Yielding` message sets it; the page never sets it) a quiet "Passing until the end of turn" ("...until the stack is empty", "...until your next turn") with a "Stop passing" button, which asks the session for `cancelYield()` and leaves the line to the server's `Yielding`. The session clears a `Priority` decision still on screen when a yield starts (the server passed for it), or, for a yield that began and ended inside one step and was never told, when the next batch moves the game on; it leaves every other decision (attackers, blockers, discards) and the clock of one it keeps.
- Response clock: a `Decision` with `deadline_ms` becomes `pending.deadlineMs`, and the session counts it down in `PlayState.clock` (`{ id, totalMs, leftMs }`) on its own `timers` (so the manual clock of the tests moves it), from the moment the message arrives: one timer, woken whenever the whole seconds left change, no matter how often the page renders. `leftMs` at a tick is what is left then; a decision sent again after a reconnect arrives with what is left, so `totalMs` is that. Any change of `pending` (an answer, a snapshot, a lost connection, a new decision) stops the old clock and starts the new one, and at zero the session clears `pending` itself: the server has answered for the seat by then, and a prompt left on the screen would only invite an answer that is stale. `prompt/ResponseClock` (inside the decision line, under every kind's prompt, drawn only while `clock.id` is the prompt's decision) shows "Passing for you in 7 s" or "Declaring no blocks in 31 s" (`clockText.ts`), a `role="timer"` that does not announce each second, a bar that drains over the time left (the `response-clock-bar` utility in `prompt/responseClock.css`, imported by `index.css`: a CSS animation of `animation-duration` = the time left at mount, `--clock-from` = the part that was left, declared only inside `prefers-reduced-motion: no-preference`, and not drawn at all under a preference for less motion, where the number alone changes once a second) and one polite sentence for a screen reader when it appears. The last three seconds are urgent (`data-urgent`, the text turns red; the words say it too). Dev: `/dev/table?prompt=priority-clock|block-clock` (the full time, not ticking). Tests: `play/clock.test.ts` (the session on a manual clock), `prompt/ResponseClock.test.tsx`, `prompt/clockText.test.ts`, `responseClockCss.test.ts`.

The seat's stops and Full Control on the screen and from the keyboard, in `features/table/stops/` and `play/session.ts`. The page shows what the server holds and never flips a stop or a mode before the server says so.

- Store: `stops` (a list of `{side, step, keep}`; `keep` true is a lasting stop, false one that goes once its step has passed) and `fullControl` (`Off`, `NextWindow`, `Held`) are replaced whole by every `Welcome`, `Stops` and `FullControl` message and survive a dropped connection until the next `Welcome`. `net/parse.ts` checks a stop (known side and step, boolean `keep`), a list (each side and step once) and a mode; a missing field is a bad shape.

## Accounts and games pages

Sign-in on top of the server's accounts (`server.md`, Accounts; bodies `protocol.md`, REST bodies). Guests are unchanged: a seat link opens a seat with no account, and a server without `DATABASE_URL` (503 `accounts_unavailable`) leaves the whole app as it was, with no sign-in offered anywhere.

- Client: `net/accounts.ts` `createAccountsApi({fetch, baseUrl})` (shared `accountsApi`): `register`, `login`, `logout`, `me`, `myGames`, every request with `credentials: 'include'`. Bodies are the generated `Credentials`, `UserView` and `MyGames` and are checked at runtime; a failure is an `AccountError {code, status, retryAfter}` with the `AuthErrorCode` of the server plus local `unknown`, `network`, `bad_response` (`AUTH_ERROR_CODES` is a `Record` over the generated union, so a new code stops the build until it has words). `Retry-After` seconds are kept for the 429. `api.createGame` sends the cookie too, which is what binds seat 0 to the creator.
- Store: `features/auth/store.ts` `createAuthStore({api, initial})`, a vanilla zustand store; `context.ts` holds `appAuth` (the app's, given to `AuthProvider` in `main.tsx`, which calls `start()` once), `useAuth(selector)` and `useAuthStore()`. A page without a provider (most tests) gets a stand-in store whose status is `unavailable`, so it behaves as before accounts. `status` is `loading` until `GET /api/auth/me` answers, then `signed-in` (200), `signed-out` (401, and also a network, 5xx or unreadable answer, since nothing is then known to be signed in) or `unavailable` (503 `accounts_unavailable`, also when a register, login or games call says so). `register` and `login` return `{ok, user} | {ok: false, error}` and change nothing on a failure; a password lives only in the request. `logout` clears the user, the games and any notice; a failed sign-out keeps the user and sets `notice` (shown under the header with Dismiss), since a cookie that is still alive must not look signed out. `games` is the My games list (`idle | loading | ready | failed`, newest first whatever order the server used, the old list kept while reloading or after a failure); `loadGames` turns a 401 into `signed-out`. An answer that arrives after who is signed in changed, or after a newer question, is dropped (`round` counter).
- Forms: `/login` and `/register` (`AuthScreen`, `AuthForm`): username 3 to 32 of letters, digits, `_`, `-` and password 10 to 128 characters (`rules.ts`, copies of the Rust constants), shown under the fields and checked before anything is sent, nothing trimmed. The fields are uncontrolled, so the password is in no React state: it is read at submit, sent, and the input emptied once the answer is in, whatever it was; state holds only the words of the problems. Every `AuthErrorCode` has a sentence (`errors.ts`, `describeAccountError`; a wrong sign-in is one sentence that names neither half, a 429 says how long to wait from `Retry-After`) and a field: `invalid_username` and `username_taken` on the username, `invalid_password` on the password, the rest in an alert. After a failed submit focus goes to the first wrong field, else the alert; the button is disabled and the fields read-only while pending; `autocomplete` is `username`, `current-password` (login) or `new-password` (register); the form is `method="post"`. A signed-in visitor, and a successful sign-in or registration (which signs in), leave for `next` or `/` with a history replace. A server without accounts shows a note instead of the form.
- `next`: `features/auth/next.ts` `sanitizeNext` lets through only a string that starts with one `/`, has no backslash or control character (a tab or newline inside `/\t/host` is deleted by URL parsing and gives `//host`), resolves to the same site, does not start with `//` after dot segments, and is not `/login` or `/register`; the result is path and query, never the fragment (a seat token must not travel in a query string). `parseAuthSearch` is the routes' `validateSearch` and always names the key (`next: undefined` when refused): the router merges what a page validates over the raw address, so leaving the key out would let the unchecked value through. `AuthScreen` checks again before it navigates.
- Header: `AccountNav` in `AppShell`: nothing while `loading` or `unavailable`; "Sign in" and "Register" when signed out; the username (cut short, whole name as a tooltip), "My games" and "Sign out" when signed in. Signing out on `/games` goes home instead of to the sign-in form. At 390 px it fits with a 32-character name.
- `/games` (`features/games/MyGamesPage`): not signed in goes to `/login?next=/games` (replace); while `loading` it says it is checking; `unavailable` explains there is no list. A row (`GameRow`) has the state badge (Lobby, Running, Finished), how long ago (`format.ts` `timeSince`, a date after 30 days), the other players (the username of an account, else the seat name), the user's own seat, the result of a finished game ("You won", "Bo won", "Draw") and, for lobby and running games, "Rejoin": a link to `/game/<id>` with no fragment, which connects through the session. There is no "View result" link: the server drops a finished game from memory ten minutes after it ends (`GET /api/games/{id}` and `/ws/{game}` then say 404), so the game page could show it only for a moment; the row is the record. Reload keeps the old list on screen; a failed load shows the reason with "Try again" (above the old list if there is one); an empty list links to the create page.
- Create (`features/create`): the page waits until it is known who is signed in; a signed-in creator gets seat 1 named after the account, the line "Signed in as X. You will play as <seat 1 name> in seat 1; the other links are for your friends. The game will be listed under My games", and after creating a note that seat 1 is saved to the account; the list is asked for again then, so a session that ended shows up as a signed-out header and the note goes. The seat links flow is unchanged for everyone.
- Game page: `GameRoute` reads the seat link from the fragment as before. With one, `GamePage` joins by token, whoever is signed in (the server binds an unbound seat to the signed-in visitor on the way in). Without one and signed in, `GamePage account=<username>` makes the socket `/ws/{game}` (`GameSocketOptions.token` left out, `socketUrl` without a token), where the cookie of the upgrade picks the seat; `Join` carries the username (the server ignores `name`), and every retry, "Use this window instead" and "Try again now" use the same address. While it is not yet known who is signed in the page says it is checking. With neither, `SeatLinkMissing` explains: open your seat link, or sign in (the link carries `next=/game/<id>`; only offered when accounts exist). A session that cannot reach the game has its own words in `ConnectionNotice` (`via="session"`: signed out, seat not saved to the account, game gone) and a "My games" link. Signing out on a session-connected page drops the connection and shows the explanation.
- Lobby: `useSeatAccounts(game, seat, refreshKey)` asks `loadGames` when the lobby opens and whenever the connected seats change, and reads this game from the list: other seats with an account show "signed in as <username>", this seat shows it too and a note "This seat is saved to your account" once the list confirms it. A guest sees nothing and the list is never asked for; a failing list is silent.

### End-to-end

`pnpm e2e` (`playwright.config.ts`) starts `cargo run -p mtg-server` (an empty `DATABASE_URL` gives the in-memory store and the built-in demo decks) on port 8301 and `pnpm build` plus `vite preview` on port 5301, both new for every run.

- `E2E_SERVER_PORT` and `E2E_WEB_PORT` override the ports (`e2e/ports.ts`) to run several suites at once. `E2E_REUSE=1` keeps servers already listening there; `E2E_TRAIL=1` prints every answered decision; `--repeat-each=N` repeats the game.
- On NixOS Playwright's own browser cannot run. Point `CHROMIUM_PATH` at the Nix chromium with a glob, because the store path changes with every update: `CHROMIUM_PATH=$(ls -d /nix/store/*-chromium-[0-9]*/bin/chromium | head -n 1) pnpm --dir web e2e`.
- `full-game.spec.ts` (`driver.ts`) plays both seats through the real UI. A seat waits for a `[data-decision]` with a new `data-decision-id` (the id tells two Priority prompts apart), reads its legal cards (`data-highlight="legal"`) and answers with real clicks. There are no sleeps: waits are `waitForFunction` polls. The engine seed is random per game.
- `accounts.spec.ts` needs Postgres. With `E2E_DATABASE_URL` set to an empty scratch database (the server migrates it on boot) the config also starts a second server on port 8302 and a second preview on 5302 (`E2E_ACCOUNTS_SERVER_PORT`, `E2E_ACCOUNTS_WEB_PORT`). Without it `pnpm e2e` stays hermetic and the spec is skipped. Usernames are random per run, so one database serves many runs.

```sh
docker compose exec db psql -U magic -c 'create database magic_scratch'
E2E_DATABASE_URL=postgres://magic:magic@localhost:5432/magic_scratch pnpm --dir web e2e e2e/accounts.spec.ts
docker compose exec db psql -U magic -c 'drop database magic_scratch'
```

To try the account screens by hand, run the server on that database (`DATABASE_URL=… MTG_BIND=127.0.0.1:8318 cargo run -p mtg-server`) and the dev server in front of it (`MTG_SERVER_URL=http://127.0.0.1:8318 pnpm --dir web dev --port 5318`). `ui-shot.mjs` cannot set a cookie, so a signed-in page needs Playwright.

## Conventions

- Server state is shown, not predicted: ready, stops, Full Control and yields change on screen only when the server says so.
- Colour never carries meaning alone, and live regions are polite. A row of cards, a ladder row or a list is one tab stop (arrows, Home, End); a control that must keep focus when it cannot act is `aria-disabled`, not `disabled`.
- Every animation sits inside `@media (prefers-reduced-motion: no-preference)` (`fx.css`, `combat.css`, `responseClock.css`, the `your-turn-cue` utility of `index.css`); under `reduce` an effect is a still highlight, the clock bar is not drawn and the tab title does not flash. JS reads `useReducedMotion` or `prefersReducedMotion`. A CSS test per file (`fxCss.test.ts`, `combatCss.test.ts`, `responseClockCss.test.ts`, `yourTurnCss.test.ts`) fails when an animation leaves the media query.
- A component's stylesheet sits beside it. Colours are tokens with a light and a dark value; Tailwind class names are written whole so Tailwind can see them.
